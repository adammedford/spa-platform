## Answer

**What landed** (branch `task/2.1-registry-validator`, worktree `/Users/adammedford/spa-worktrees/ws2-hosting`):

- `src/Platform.Registry/RegistryValidator.cs`: `Validate(string document, PlatformPolicy policy, long? liveRevision) -> RegistryValidation` and `ValidateAppDefinition(string, PlatformPolicy) -> AppDefinitionValidation`. Pure and static. Order: strict parse (a property named twice is refused), then the registry schema, then every rule from contracts/README.md "Rules that JSON Schema cannot express" that is task 2.1's. The rules are revision > live, unique appId, host and clientId, apis[].name unique within the app, host suffix, upstream policy, issuer known, and port <= 65535 on host and upstream. Every error is collected, not just the first. Any error means `Apps` is empty, so the document is rejected whole.
- `RegistryValidation`: Revision, Apps (`AppDefinition` records), Errors and Warnings kept apart, `IsValid`, and `ToSnapshot(etag)` for task 2.2. More than one upstream origin is a warning (`multiple-upstream-origins`).
- `RegistryIssue(Rule, Path, Message)` plus `RegistryRules` constants. Path is a JSON pointer.
- `RegistrySchemas.cs`: the four contract schemas are loaded into one JsonSchema.Net registry with the registry schema first. Output is hierarchical, so a passing `contains` or `not` does not report its children. The schemas are embedded from byte-for-byte copies in `src/Platform.Registry/Schemas/`, because `src/Gateway/Dockerfile` copies only `src/` into its build stage. `SchemaCopyTests` fails when a copy differs from `contracts/` (checked by mutating a copy and watching it fail).
- `EntryFingerprint.cs`: `sha256:` plus the hex of the canonical JSON. Members are sorted ordinally, array order is kept, whitespace is compact, and scalars are rewritten from their parsed values.
- `HostPolicy.cs`: suffix match at a label boundary, port bound, and origin normalisation.
- Tests in `tests/Platform.Registry.Tests`: 42 tests. Each rule from the README table has a passing and a failing case built from `contracts/*.example.json` and `fixtures/apps/*.json`. The validator tests run a representative set of schema rules: schemaVersion, an unknown property, session bounds, `openid` missing from scopes, and every forbidden CSP source. The exhaustive schema-rule cases are in `tests/Contracts.Tests/RegistryRuleTests.cs`, against the same schema files.
- `contracts/changes/2.1-registry-schemas-and-jsonschema-net.md` (Status: open, does not block 2.1). It asks for two things: `docs/dependencies.md` should name Platform.Registry as a JsonSchema.Net user, and, optionally, the Dockerfile could copy `contracts/*.schema.json` so the copies can be dropped.

**Seams (chosen by implementer):** `RegistryValidator.Validate` and `RegistryValidator.ValidateAppDefinition` (the public entry points that the gateway's registry source and `spactl` call), `RegistryValidation.ToSnapshot`, and the fingerprint as observed on `AppDefinition.Fingerprint`. No test reaches into internals.

**Decided by implementer:**

D-1's recommendation to keep the engine out of the gateway is marked as a narrowing that the integrator must accept, and that has not happened. Only `RegistrySchemas.cs` touches the engine. D-1 stays open.
2. Phase 1 upstream policy is equality of origins after Uri normalisation: case, and a default port dropped. It is not a pattern match.
3. A host suffix that does not begin with "." must still meet the host at a label boundary.
4. The CSP wildcard-in-host rule is not added. The README says a change request is the way to add it.
5. `AddPlatformRegistry` registers nothing for 2.1 because the validator is static. Binding `PlatformPolicy` from configuration is left to task 2.2.
6. A document with a duplicate JSON property name is rejected (not-json), so the schema and the model never read different values.
7. Schemas are embedded from guarded copies in src/Platform.Registry/Schemas, not linked from contracts/, so the gateway image still builds. The change request offers the alternative.
8. The app-definition check is included, with the schema and the single-entry policy rules, for `spactl app add` (task 2.6).
9. The gate command's `-exec dirname {} ;` would not parse under zsh, so it was run with `\;`. The meaning is unchanged.

### Spec axis
- **Fixed (verified by a run).** "Errors and warnings kept apart" and "rejected whole" assume `Validate` always returns a result. It threw on schema-valid documents instead. Draft 2020-12 calls `30.0` and `3e1` integers, and the schema puts no maximum on `revision` or `timeoutSeconds`. I ran a probe test in `tests/Platform.Registry.Tests` with these inputs. `revision: 42.0`, `timeoutSeconds: 30.0`, `timeoutSeconds: 3e1`, `lifetimeMinutes: 480.0` and `revision: 99999999999999999999999` each threw `InvalidOperationException` ("An element of type 'Number' cannot be converted to a 'System.Int64'"). `timeoutSeconds: 1000000000000` threw `ArgumentOutOfRangeException` from `TimeSpan`. That breaks the result contract that task 2.2's source and `spactl` call.
  - Fix: new `src/Platform.Registry/JsonInteger.cs` reads any integral spelling that fits in an Int64. A value too large for the model now comes back as error `integer-out-of-range` at its JSON pointer: past Int64 for `revision`, past `TimeSpan` (922337203685 s) for `timeoutSeconds`. It is no longer an exception.
  - Tests added: `An_integer_spelled_with_a_fraction_or_exponent_is_accepted` (3 cases), `An_integer_the_model_cannot_hold_is_an_error_not_an_exception` (3 cases), `The_longest_timeout_a_TimeSpan_holds_is_accepted`.
- **Fixed, same cause.** "Two loads of one document give equal fingerprints" held, but `EntryFingerprint` wrote numbers from their raw text. - The new rule is not a row in the README table, so I added section 3 to `contracts/changes/2.1-registry-schemas-and-jsonschema-net.md`. It is optional and does not block: either a README row or a schema `maximum`.

The byte-for-byte guard (`SchemaCopyTests`) keeps the copies equal to the contract. I accept this as meeting "every rule has a passing and a failing case".
