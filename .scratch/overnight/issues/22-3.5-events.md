## Comments

**Integrator, 2026-10-14, from the decision on change request 6.4.** `IRequestTelemetryFeature` and
`SessionRef` are now in `src/Platform.Abstractions`, and this task is one of the places workstream 3
writes them. Nothing to do before `contracts-v1`; read this when the task opens.

- **`SessionRef`.** `contracts/telemetry.md` puts `session_ref` on the request line and defines it as
  the first 12 hex characters of a SHA-256 of the session key. Compute it with `SessionRef.Of`, never
  by hand, and set it on `context.Features.Get<IRequestTelemetryFeature>()?.SessionRef`. The session
  key must not reach stage 2 or any log line: it is on the contract's never-logged list. Workstream 3
  is named as the writer because only it holds the key; the request's own "3.4 and 3.9" was wrong,
  since `ISessionStore` has no `HttpContext`. Where exactly to write it is this workstream's design,
  and plan row 3.3's ticket-store adapter is the code that holds both the key and the request.
- **`auth.callback` and `auth.session`.** These two rule ids in `contracts/request-gate.md` are
  written by nothing yet. Whichever stage rejects under one sets it on the same feature's `Rule`,
  null-conditionally. Stage 2 logs it and counts `security.rejections` from it; do not declare that
  instrument here.
- **Task 4.2's 401 is not a rejection** and leaves `Rule` null, which is the precedent if a similar
  case comes up here: a 401 that reports the session's state is not a broken rule, and no new rule id
  may be invented without a gate.
