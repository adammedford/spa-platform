## Answer

**Landed** on `task/3.2-oidc-options` (`a96f04c`, forked from `overnight/2026-10-16` at `992fd8c`):

- `src/Platform.Identity/OidcOptionsSetup.cs`: `IConfigureNamedOptions<OpenIdConnectOptions>` keyed by `oidc:{appId}`. App from the pinned `IAppFeature` when it matches, else `IRegistry.Current`. Client id and preloaded secret (`IClientSecretSource.Get`, no I/O), code + `ResponseMode = query` + PKCE, `SaveTokens`, `MapInboundClaims = false`, entry scopes and `Resource`, `CallbackPath = /signin-oidc`, `SignInScheme = cookie:{appId}`, `__Host-spa-corr.` / `__Host-spa-nonce.` on `Path=/` (Secure, HttpOnly, Lax, no Domain), `RemoteSignOutPath` cleared, then the issuer's `IIdpProfile.Configure`. Also `OidcOptionsValidation`: runs the handler's `Validate(name)` for every `oidc:` name (R-D9).
- `src/Platform.Identity/IssuerDirectory.cs`: reads `Issuers:{name}` into `IssuerDefinition`. It builds one `SharedOidc` per issuer, holding one backchannel `HttpClient` and one `ConfigurationManager<OpenIdConnectConfiguration>`.
- `AddPlatformIdentity` registers the directory, the setup, the validation and the framework's `OpenIdConnectPostConfigureOptions`, the same way `AddOpenIdConnect` would.
- Tests in `tests/Platform.Identity.Tests`: `ChallengeTests` (S-A1, S-A2, R-A1, R-A2), `OidcOptionsTests` (R-D9, the sharing that R-A7 relies on, profile consulted), `LoginTests` (R-D4 full login, R-A7 fetch counts, R-D2/N-27 GET and POST). The shared harness is `IdentityGateway.cs`. The 3.1 tests now run on that harness.
- Mutations (each failed its guard, then reverted): validation removed failed 1 of 31; `RemoteSignOutPath` left live failed 3; per-app metadata failed 2; `form_post` default failed 1; default login-cookie path failed 1.

**Seams (chosen by implementer):**
1. `AddPlatformIdentity` plus `IOptionsMonitor<OpenIdConnectOptions>.Get(SchemeNames.Oidc(appId))`. This is how the framework itself obtains options.
2. One request on a pinned host through the framework's `UseAuthentication`, checked by what it returns: the redirect query, the Set-Cookie headers and the status. It runs against the real `fixtures/TestIdp` (the test project now references it; A-01 covers only the gateway).

**Decided by implementer:**
- If no `IIdpProfile` is registered under the issuer's configured name, the options keep the plain OIDC settings and no profile is applied. No profiles exist until task 3.7, and with a throw here every pinned request in the composed gateway answered 500 (47 composed tests failed in the first gate run).
- Plain-HTTP metadata is allowed only to a loopback IP address (the hermetic test provider). Any other authority must be https, as the platform-config schema already requires.
- The code exchange keeps the handler's form-body client secret. `ClientCredentialStyle` is not applied to the code exchange here. Cognito accepts either style there (C-2.21), and doing it would mean hand-written token-request code. 3.8 maps the style for refresh and revocation.
- Tests find the session cookie by elimination rather than by name, because task 3.3 sets the name.

**Gate:** `GATE: GREEN`, total 1241, failed 0, succeeded 1241 (log `.scratch/overnight/log/3.2-implement.txt`).

Outstanding: task 3.7 registers the `standard` and `cognito` profiles. Once both exist, it may make a missing profile fail rather than fall back to the plain settings.
