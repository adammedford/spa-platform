## Answer

Landed on `task/3.4-session-store` (commit "Task 3.4: the in-memory session store, bounded, swept and registered by AddPlatformIdentity"), forked from `overnight/2026-10-16` at `dc14faa`.

- `src/Platform.Identity/MemorySessionStore.cs`: the Phase 1 `ISessionStore`. 256-bit random base64url keys; serialized ticket bytes kept as given; versioned replace under one lock; a session past `ExpiresAt` reads (and replaces) as absent; a `TimeProvider` timer sweeps expired sessions every minute; `Session:MaxSessions` bounds it; `RemoveAppAsync` purges one app.
- `src/Platform.Identity/PlatformIdentityExtensions.cs`: `AddPlatformIdentity` registers it with `TryAddSingleton`, built on first use from `Session:Store` (must be `memory`) and `Session:MaxSessions` (whole number >= 1), with the registered `TimeProvider` or the system clock. A host that registered its own store first keeps it.
- `src/Platform.Identity/Platform.Identity.csproj`: `InternalsVisibleTo` for its own test project.
- Tests in `tests/Platform.Identity.Tests`: `MemorySessionStoreContractTests` (the Platform.Testing `SessionStoreContract`, unchanged, 11 tests), `MemorySessionStoreTests` (expiry, sweep, bound, concurrency), `SessionStoreRegistrationTests`.
- Mutations: a sweep timer that does nothing failed 1 of 80; treating the expiry instant as live failed 3 of 80; removing the eviction failed 4 of 80.

Seams (chosen by implementer):
- `ISessionStore` as implemented by `MemorySessionStore`, on a `FakeTimeProvider` (the contract suite plus store-specific behaviour; `Count` is the one internal read, for the sweep's memory effect).
- `AddPlatformIdentity` -> resolved `ISessionStore`, driven by configuration.

Decided by implementer:
- At the bound a login succeeds and the session nearest its expiry is evicted (an expired one first), rather than the login failing.
- Sweep interval one minute; expiry is inclusive (`ExpiresAt <= now` has ended).
- The store is built lazily, not validated at start-up, because `tools/smoke.sh` and the health check run with no session settings; an unsupported `Session:Store` or bad `Session:MaxSessions` throws on first session use.

Gate: `GATE: GREEN`, log `.scratch/overnight/log/3.4-implement.txt`; last summary: total 1323, failed 0, succeeded 1323, skipped 0.

The behaviour is exercised: the sweep test removes 2 of 3 entries and the purge test removes 2 of 3, and both pass in the gate log. ### Spec
- Row 3.4 says "serialized tickets, versioned replace, a capacity bound, an expiry sweep, purge by app" and "A store contract suite passes". All five are present. `MemorySessionStoreContractTests` subclasses `Platform.Testing.SessionStoreContract` unchanged, and it is green. Both acceptance boxes stay ticked.
- **Skipped, not a defect:** the store keeps the caller's `Ticket` bytes without copying them. `ReadOnlyMemory<byte>` gives readers no way to write. The writer (the 3.3 ticket-store adapter) serializes fresh bytes for each call, and the comment says so.
- **Skipped, decided by the implementer and reasonable:** `Session:*` is validated lazily, so a bad setting fails on first session use rather than at start-up. `src/Gateway/appsettings.json` has no `Session` block, but `contracts/platform-config.schema.json` requires `Store` and `MaxSessions`. Validating at start-up would therefore break `tools/smoke.sh`.
- **Outstanding for the integrator, not 3.4's to fix:** add `"Session": { "Store": "memory", "MaxSessions": 10000 }` to `src/Gateway/appsettings.json` before task 3.3 routes the cookie handler through `ISessionStore`. Without it, the first login in the composed gateway throws.
- No scope creep. Registering the store in `AddPlatformIdentity` is workstream 3's entry point, and `InternalsVisibleTo` is in its own project.
