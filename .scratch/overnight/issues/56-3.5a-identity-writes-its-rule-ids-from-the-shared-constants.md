# 56: 3.5a — Identity raises `auth.callback` and `auth.session` from the shared constants
**Task:** 3.5a
**Owner:** ws3-identity
**Blocked by:** I-6, 3.5, 3.9
**Status:** resolved

**What to build:** Nothing new — a constraint on work that has not started yet, filed now so the
fourth copy of the rule ids is never written.

`contracts/request-gate.md` lists two ids that only workstream 3 can raise:

| Rule id | Fires when |
| --- | --- |
| `auth.callback` | Any refused login callback |
| `auth.session` | A cookie that resolves to no session for this app |

`Platform.Abstractions.RuleIds` already declares both (integrator's decision, ADR-0015, 14 October
2026), so when `src/Platform.Identity` writes them it reads `RuleIds.AuthCallback` and
`RuleIds.AuthSession` and declares no constant of its own. Set them on
`IRequestTelemetryFeature` the way the other owners do, null-conditionally:

```csharp
context.Features.Get<IRequestTelemetryFeature>()?.Rule = RuleIds.AuthSession;
```

Contracts: `contracts/request-gate.md` -> Rule ids; `contracts/telemetry.md` -> "How `rule` and
`session_ref` reach the request line", which also assigns `session_ref` to this owner, since only
workstream 3 holds the session key.

## Acceptance
- [x] The shell gate and the `/bff` callback set their id from `Platform.Abstractions.RuleIds`
- [x] `src/Platform.Identity` declares no rule id string of its own
- [x] A test per id, able to fail, using `SettableRequestTelemetryFeature` from `Platform.Testing`
- [x] `session_ref` is set from the same feature, and no session key reaches a log line (N-16)

## Answer

Landed on `task/3.5a-identity-writes-its-rule-ids-from-the-shared-constants`, commit `2d7ac6a`
(fork `67f0115`). Every change is in `tests/Platform.Identity.Tests`. Tasks 3.5 and 3.9 had already
written the production code this ticket constrains: `AuthenticationEvents.OnRemoteFailure` sets
`RuleIds.AuthCallback`, `Bff.NoteDeadSession` (the shell gate and `/bff/session`) sets
`RuleIds.AuthSession`, and `AppBoundTicketStore` sets `SessionRef.Of(key)`. All three are
null-conditional on `IRequestTelemetryFeature`, so no source change was needed.

- `SharedRuleIdsTests.cs` (new) scans `src/Platform.Identity` and fails on any id from `RuleIds.All`
  spelled as a string literal. A planted case shows the scan can fail. This is the same guard the
  ws4 test projects have.
- Per-id tests now compare against the contract's literal strings `"auth.callback"` and
  `"auth.session"` instead of the constant. They are in `AuthenticationEventsTests`, `ShellGateTests`
  and `BffLogoutTests`, and they run against `SettableRequestTelemetryFeature`.
- `AccessTokenSourceTests.The_session_key_reaches_no_log_line_and_its_reference_reaches_the_request`
  (new) follows one session through sign-in, refresh, a shell request and logout. It checks that
  session_ref is `SessionRef.Of(key)`, that the refresh log line carries the reference, and that the
  key appears in no log line (N-16).
- Mutation check: I broke the code three ways, a literal in Bff, the wrong id in the callback, and
  the raw key as session_ref. Each one turned these tests red. I then restored the code.

Seams (chosen by implementer): `IRequestTelemetryFeature` via `SettableRequestTelemetryFeature`, the
existing `IdentityGateway` harness, and `ILoggerProvider`, which `CapturingLoggerProvider` captures.
The guard reads the source files themselves.

Decided by implementer: the per-id assertions use literals rather than `RuleIds`, following the
convention the ws4 guards document. If both sides read the constant, a wrong-but-consistent id would
pass.

Gate: `total: 1412  failed: 0  succeeded: 1412`, GATE: GREEN.
