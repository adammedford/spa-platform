### Facts established first (read from the repo, not asked)

- **The engine is in the gateway process, through one file.** `src/Platform.Registry/Platform.Registry.csproj` references `JsonSchema.Net` with no version (the pinned 8.0.5). The only file that uses it is `RegistrySchemas.cs`. `RegistryValidator` (the gateway path) and `ContractDocuments` (`spactl`'s infra-outputs, platform-config, `appId` and `release` checks) both go through it.
- **`spactl` has no direct reference.** `tools/spactl/spactl.csproj` references `Platform.Abstractions`, `Platform.Registry` and `AWSSDK.S3`. It reaches JsonSchema.Net only through `Platform.Registry`. So the direct users are `tests/Contracts.Tests` ("Schema tests"), `fixtures/Fixtures.Tests` (Q45) and `src/Platform.Registry`. Q52 left `spactl` in the row "for task 2.1 to settle", and 2.1 has now settled it.
- **CR-5.5's edit to the same cell has not been applied.** On both `main` and the integration branch, `docs/dependencies.md:63` still reads "Schema tests, `spactl`". Q45 (add `Fixtures.Tests`) and this request edit the same cell.
- **D-1's recommendation conflicts with a contract sentence.** D-1 recommends keeping the engine out of the gateway and having the gateway check "through its typed model and the rule validator", and it calls that a narrowing of 2.1. `contracts/README.md` -> "Rules that JSON Schema cannot express" says the one library exists so that "the gateway and `spactl` share so they cannot disagree". Several security rules exist only in the schema: `'*'` and `'unsafe-eval'` in every CSP directive, `'unsafe-inline'` and `data:` in `script-src`, `additionalProperties: false`, and the `host`, `upstream` and `clientSecretRef` patterns. N-14 needs a forbidden CSP source rejected whole. Without the engine, the gateway would have to re-express each of these rules in C#.
- **The plan says the gateway trusts the registry.** `docs/plan/01-plan.md`: "The gateway trusts the registry and the identity provider, and nothing that arrives from a browser". The engine therefore parses a trusted document, which lowers the cost of running an older release line in-process.
- **The Dockerfile copies `src/` only.** `src/Gateway/Dockerfile` copies the root build files, each `*.csproj`, then `COPY src/ src/`, and publishes. It does not copy `contracts/`. There is no `.dockerignore`. The build context is the repository root ("Build from the repository root"), so `contracts/` is available to a `COPY`. `tests/Platform.Registry.Tests` already links `../../contracts/*.schema.json` and the examples, so linking from a project is established practice.
- **The copies and A-05 cannot both hold through I-6.** `SchemaCopyTests` fails when `src/Platform.Registry/Schemas/<file>` differs from `contracts/<file>`. `OWNERSHIP.md` gives `/src/Platform.Registry/` to ws2-hosting. `.github/path-ownership.py` (A-05, pre-push) fails a push whose diff from the merge base touches more than one owner's paths. Q34 (answered yes) has I-6 flip three schema files to `frozen-at-g1b` and drop the root `exceptions`, which changes their bytes. The integrator cannot also refresh the copies in the same push without `--no-verify`. If the copies are refreshed in a separate push, one of the two merges fails CI. So "a contract change needs its copy refreshed in the same merge", as the request puts it, cannot be done within the ownership rules.
- **The schemas are frozen.** `registry.schema.json` carries `x-freeze: frozen-at-g1a` with only `#/$defs/oauth` excepted. A `maximum` on `revision` or `timeoutSeconds` would narrow a frozen contract. Adding a README row is prose, which I-7's decision lets land without a gate.
- **The README states that `timeoutSeconds` is unbounded.** `contracts/README.md:106`: "`timeoutSeconds` has no upper bound, because the plan states none". The schema description says the same. `session.lifetimeMinutes` already has `maximum: 720`, so it is not affected.
- **The validator's timeout bound is not the runtime's.** `RegistryValidator.cs:30` sets `MaximumTimeoutSeconds = TimeSpan.MaxValue.Ticks / TicksPerSecond` (922337203685). `src/Platform.Proxy/RegistryProxyConfig.cs:68` passes the value to YARP as `ForwarderRequestConfig.ActivityTimeout`. The YARP 2.3.0 binary references `CancelAfter` alongside its `ActivityCancellationTokenSource`. The .NET 10.0.12 reference documentation for `CancellationTokenSource.CancelAfter(TimeSpan)` says it throws `ArgumentOutOfRangeException` when the delay "is less than -1 or greater than Int32.MaxValue (or UInt32.MaxValue - 1 on some versions of .NET). Note that this upper bound is more restrictive than TimeSpan.MaxValue." Int32.MaxValue milliseconds is about 2,147,483 seconds (24.8 days). I read this and did not run it. So a `timeoutSeconds` between about 2.1 million and 922 billion is schema-valid and validator-accepted, and could still throw when YARP applies it. Whether YARP's own configuration validation catches it first is unverified.
- **The ALB is another ceiling, still unknown.** The ALB idle timeout would cut a silent upstream first in the deployed tier. `infra/modules/cell` is empty because task 1.3 has not landed, so the value is unknown. It does not change the hermetic bound.
- **A code comment will go stale.** `src/Platform.Registry/RegistryIssue.cs:18` and the `IntegerOutOfRange` summary say "Not a README row". They become false once Q3 lands.
- **Precedent for closing.** I-7 and 1.6a use the `decided, <date>` Status line and a `## Decision` section. Q46 applies the same form to CR-5.5.

## Proposed glossary / ADR

### Glossary (proposed, not applied)

- **Schema check**: evaluating a document against its contract schema, which is the part of registry validation a JSON Schema engine performs. Distinct from the **validator's rules**, the checks in `contracts/README.md` -> "Rules that JSON Schema cannot express". Together they are **registry validation**, which the gateway and `spactl` run through one shared library. Avoid "schema validation" for the whole, because the gateway's acceptance of a document is more than its schema. *(The plan row says "schema check" and D-1 says "the rule validator", and neither term is defined. Q1 depends on telling the two apart.)*

### ADR candidates

None. D-1's close (Q1) is a real trade-off, between licence, release-line age and one rule set, and it may surprise a reader who sees a pinned old major. But it is not hard to reverse: `RegistrySchemas.cs` is the only file that touches the engine. Criterion 1 fails, so the decision and its trigger go in `docs/dependencies.md` (Q7). The Dockerfile `COPY` (Q2) is one line (criterion 1 fails). The integer row (Q3) is not surprising (criterion 2 fails).
