# 68: 6.1a — `UpdateRegistryAsync` reports `NotModified` when the poller's first tick lands first
**Task:** 6.1a
**Owner:** ws6-verification
**Blocked by:** None
**Status:** resolved

**What to build:** Make `GatewayHarness.UpdateRegistryAsync` and `PublishRegistryAsync`
(`tests/Gateway.TestHarness/GatewayHarness.cs`) report the outcome of the write they made, not of the
one poll they ran. On CI run https://github.com/adammedford/spa-platform/actions/runs/38849080050
(`main` at `55c4599`, a docs-only commit) two rows failed with `Expected: Swapped / Actual:
NotModified`: `UpstreamResponseTests.StartWith` (`Negative/UpstreamResponseTests.cs:136`) and
`UnknownApiTests.An_api_name_another_app_lists_is_still_unlisted_for_this_one`
(`Negative/UnknownApiTests.cs:106`). The re-run of the same commit passed, and the suite passes
locally (90 of 90, Debug, arm64). Task 6.1 is landed; this is a carve of its harness, named `6.1a` as
`6.2a` and `6.3a` were.

**Why, as the integrator reads it (confirm by reproduction before changing anything):** the hosted
poller's first tick is not ordered against the start-up settle. `GatewayHarness.Create` writes
revision 1, starts the server, then polls once "to wait out the first read" (the comment at
`GatewayHarness.cs:230`). If the poller's first tick has not begun by then, the explicit poll *is* the
first read and the tick runs later. On a slow runner it lands between a test's write and that test's
own poll: the tick swaps revision 2 in the background, the explicit poll's conditional GET then
answers 304, and `RegistrySource.RefreshOnceAsync` reports `NotModified`
(`src/Platform.Registry/RegistrySource.cs:116`) for a document that is live. The source runs one poll
at a time (`RefreshAsync` takes `polling`), so the two cannot interleave inside a poll; they
interleave around it.

**Done when:** a test in `tests/Gateway.IntegrationTests/Harness/`, beside `HarnessBootTests`,
reproduces the race deterministically (hold the write until a background refresh is forced first, or
drive `RefreshRegistryAsync` concurrently with the write) and is watched failing on the current
harness; then the harness passes it by reporting `Swapped` whenever the live snapshot's revision, or
ETag, equals the one just written, and `NotModified` only when it does not. `Failed`, `Rejected` and
`Missing` are unchanged. The two CI rows need no edit. Owner paths only: `tests/Gateway.TestHarness`
and `tests/Gateway.IntegrationTests`. Nothing in `src/` moves: the source's semantics are right, and
the harness's reading of them is what is wrong. If the reproduction shows a different mechanism,
record it under `## Answer` and fix that instead.

## Answer

Landed on `task/6.1a-harness-update-registry-race` as `34ff5be` (fork `0d27c7d`, overnight/2026-10-16).

**Mechanism: confirmed, in forced form.** A poll that is in flight when the harness writes holds the
source's one-poll lock; it reads the new object and swaps it in, and the harness's own poll then
answers 304, so `RefreshOutcome.NotModified` came back for a live revision. Forcing a poll into that
gap reproduces CI's exact failure (`Expected: Swapped / Actual: NotModified`) on every run. (In the
local run the poller's first tick happened to land before `StartAsync`'s settle poll; on a slow
runner it lands later, which is the CI case. The forced test does not depend on which.)

- `tests/Gateway.IntegrationTests/Harness/HarnessRegistryRaceTests.cs` (new, beside `HarnessBootTests`):
  a `ReadGate` wraps the harness's `IObjectStore` through `GatewayHarnessOptions.ConfigureServices`
  (as the negative suite's `ObjectStoreRecorder` does) and holds the next registry read. The test
  starts a poll, waits until it is held, starts `UpdateRegistryAsync`, waits for the write to land in
  the bucket, then releases. Watched failing on the old harness; passes now. A second test writes
  an invalid document into the same gap and asserts the outcome is not `Swapped` (the background poll
  rejected it; the harness must not overstate).
- `tests/Gateway.TestHarness/GatewayHarness.cs`: `PublishRegistryTextAsync` (and so
  `PublishRegistryAsync`, `UpdateRegistryAsync`, `OnboardAsync`) records the ETag of its own write
  under the write lock, and maps a polled `NotModified` to `Swapped` when `Registry.Current.ETag`
  equals it. Every other outcome (`Failed`, `Rejected`, `Missing`, `SecretsUnreadable`, `Swapped`)
  passes through unchanged. Nothing in `src/` changed; the two CI rows are unedited.

Seams (chosen by implementer): `GatewayHarness.UpdateRegistryAsync` / `PublishRegistryTextAsync`
(the harness's public interface), with the race driven through `RefreshRegistryAsync` and an
`IObjectStore` wrapper installed via `GatewayHarnessOptions.ConfigureServices`.

Decided by implementer:
- Compare by ETag, not revision: the ETag identifies the exact write, also for a text document that
  has no parseable revision.
- The second (rejected-document) test is added as a guard that the fix reports `Swapped` only for a
  write that is live.

Gate: GREEN, `total: 1502 failed: 0 succeeded: 1502 skipped: 0` (log
`.scratch/overnight/log/6.1a-implement.txt`).

**Spec axis**
- *Fixed (verified by a run).* "Report the outcome of the write they made, not of the one poll they
  ran" held only for a live write. A rejected write that the background poll read first was still
  reported `NotModified`: changing the second race test to `Assert.Equal(Rejected, ...)` failed on the

  the ticket's literal "`NotModified` only when it does not" in favour of its headline; the harness
  writes a new ETag on every write (counter ETags in the in-memory store), so a genuine `NotModified`
  for a write cannot occur. The second test now asserts `Rejected` and is renamed
  `A_rejected_update_a_background_poll_read_first_still_reports_rejected`.
