### Round 2 — adopting Q1 and Q4: what the derivation obliges

❓ **Q5 — The two roots disagree about what a cell name is, and the derivation spans both.**
`infra/bootstrap/variables.tf` validates `cell` as `^[a-z][a-z0-9-]{1,19}$` (2–20 chars, must start
with a letter); `infra/modules/cell/variables.tf` validates it as `^[a-z0-9][a-z0-9-]{0,20}[a-z0-9]$`
(2–22 chars, may start with a digit, no trailing hyphen). A cell named `9poc` or a 22-character name
is legal in the platform root and illegal in bootstrap, so the platform root would derive
`…:role/spa-platform-9poc-teardown` for a role bootstrap could never have created — and because the
ARN appears only in a policy **condition** (ADR-0014 point 2 says so approvingly), nothing fails at
apply. The failure surfaces at teardown, which is the precise failure ADR-0014 exists to prevent.

➡️ Yes: make bootstrap's regex the single definition of a cell name and tighten `modules/cell` to
match it (workstream 1's edit under `infra/`, no contract change), so a name that derives an ARN is
by construction a name bootstrap could have used.

❓ **Q6 — Should the platform root fail at plan when the role does not exist?** The derivation is

## Proposed glossary / ADR

### Proposed `GLOSSARY.md` terms

None of these exist today; the first two are consumed by four tasks and a frozen contract each.
Implementation-free wordings, for the "Work, gates and evidence" and deployment-unit sections.

- **Teardown role** — the single break-glass role per cell that may delete a published release, and
  the only exception to the rule that a release prefix is written once. It may delete and never
  write, so it cannot replace a release. Not "the operator" and not a list of principals: one role
  per cell. See ADR-0014.
- **Operator** — the human principal that applies and destroys the roots and finishes teardown by
  hand. Distinct from the teardown role, which may only delete under `apps/`, and from CI, which may
  only plan. Not "deployer" and not "admin".
- **Platform tag** — `Platform = spa-platform`, matched exactly: the tag teardown queries and P-05
  asserts returns nothing. Bootstrap resources deliberately carry a different value because they
  outlive every teardown. See ADR-0013. (Missing since yesterday's decision; the same gap as the
  teardown role.)
- **Bootstrap root** — the once-applied root holding what must outlive every teardown: the state
  bucket, the CI plan role and the teardown role. Keeps local state, because it creates the bucket
  remote state lives in.
- **Break-glass** — a permission held by a named role, used deliberately and rarely, whose use is
  the exception a contract names rather than a normal operation.

## Proposed glossary / ADR

### Proposed `GLOSSARY.md` terms

Verified absent on `origin/main`. Implementation-free wordings in the file's house style; the first
two are consumed by four tasks and a frozen contract each.

- **Amend "Cell"** (under "The unit of deployment and the unit of tenancy") with the lexical form the
  entry omits: *a cell name is 3 to 22 lowercase letters, digits or hyphens, not starting or ending
  with a hyphen — a narrower form of an appId, because the name goes into a bucket name and a load
  balancer name.* This is the gap that let two roots invent two rules; **appId** already states its
  form one entry below.
- **Teardown role** — the one break-glass role per cell that may delete a published release, and the
  only exception to the rule that a release prefix is written once. It may delete and never write, so
  it cannot replace a release. _Avoid_: "the operator", "teardown principal" for the role itself. See
  ADR-0014.
- **Operator** — the human principal that applies and destroys the roots and finishes teardown by
  hand. Distinct from the teardown role, which may only delete under `apps/`, and from the CI plan
  role, which may only read. _Avoid_: deployer, admin.
- **Platform tag** — `Platform = spa-platform`, matched exactly: the tag teardown queries and P-05
  asserts returns nothing. Bootstrap resources carry a different value because they outlive every
  teardown. See ADR-0013. (Missing since that decision; the same gap as the teardown role.)
- **Bootstrap root** — the once-applied root holding what must outlive every teardown. It keeps local
  state, because it creates the bucket remote state lives in. Defined by that criterion and not by a
  count of resources.
- **Break-glass** — a permission held by one named role, used deliberately and rarely, whose use is
  the exception a contract names rather than a normal operation.

### ADR candidates

- **ADR-0014 (drafted, uncommitted) — create the teardown role in `infra/bootstrap` and derive its
  ARN from the cell name.** All three criteria hold on the new base: **hard to reverse** (the ARN is
  named in a frozen contract's `Deny` and consumed by four unwritten tasks; moving it later is a

- **No second ADR.** Questions 9, 10, 13 and 14 belong in ADR-0014's Decision and Consequences;
  questions 2, 7 and 16 change nothing architectural; question 8 is easy to reverse before any apply
  — nothing has been applied — so it fails the first criterion and belongs in ADR-0014's consequences

## PR review amendment — 2026-10-15

This file preserves the overnight snapshot and its original questions. The final ADR-0014 and
change requests supersede these review errors in Q49, Q56, Q63, Q69 and their ticket-57 sources:

- Current Terraform at `070e3fae` defaults to `spa-platform-<cell>`, with a bucket-name override.
  The account-qualified name is proposed, not implemented; `spa-platform-<cell>-*` misses the former
  but matches the latter. Teardown grants must use the actual bucket ARN, including overrides.
- `Allow` plus `BoolIfExists: true` accepts long-term keys when the MFA key is absent. `Deny` plus
  `BoolIfExists: false` also denies federation when the key is absent. ADR-0014 now separates
  IAM-user trust (`Bool: true`) from explicitly allowlisted federated human roles whose MFA is
  enforced upstream; input validation rejects root and STS-session ARNs.
- Object Lock can be enabled on existing versioned buckets; its irreversible enablement and
  retention/bypass trade-offs, not mandatory bucket replacement, are the relevant constraints.
- Role separation protects against the ordinary writer, not a trusted human who can switch
  between teardown credentials and writer credentials. No AWS apply or live role is claimed.
- The plan-ignore patterns land here; the apply-recipe and CI artifact follow-ups remain open.
