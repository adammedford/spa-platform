## Answer

**Landed** on `task/3.3-cookie-options` (fork `d5a6f0c`), commit `7702239`, all inside workstream 3's paths.

- `src/Platform.Identity/CookieOptionsSetup.cs`: named cookie options per app, registered in `AddPlatformIdentity` beside the framework's cookie post-configuration. `__Host-spa-session`, Secure, HttpOnly, `SameSite=Lax`, `Path=/`, no Domain; `ExpireTimeSpan` = the entry's `SessionLifetime`; `SlidingExpiration = false`; the session store and cookie manager below.
- `src/Platform.Identity/AppBoundTicketStore.cs`: `ITicketStore` over `ISessionStore`. It writes `SessionRecord`s bound to app and client (Version 0 on create, +1 on renew via `ReplaceAsync`). A record bound to another app or client reads as absent: it is not returned, renewed or removed. It writes `session_ref` with `SessionRef.Of(key)` on `IRequestTelemetryFeature`, null-conditionally. It implements only the HttpContext overloads the cookie handler calls, and the others throw.
- `src/Platform.Identity/CallbackBlindCookieManager.cs`: wraps `ChunkingCookieManager` and returns no session cookie on `/signin-oidc`, so sign-in always stores a new key.
- `src/Platform.Identity/SchemeApp.cs`: the pinned-or-live app lookup, now shared by the OIDC and cookie setups. `OidcOptionsSetup` behaviour is unchanged.
- Tests in `tests/Platform.Identity.Tests`:
  - `SessionCookieTests`: S-B1, S-B3, S-B4, R-A8, lifetime and no sliding.
  - `SessionIsolationTests`: S-A4 to S-A6, R-A3 to R-A5, S-B2, R-A9, S-B4 (client binding), S-B5 to S-B7, R-A10, N-01, N-02, N-18, R-D6, N-21, session_ref.
  - `CallbackRejectionTests`: S-C1 to S-C4, R-B1 to R-B5, N-03 to N-05, plus an intact-callback control.
  - The harness (`IdentityGateway`) gained an `/api/probe` stand-in, a `RecordingSessionStore` over Platform.Testing's `InMemorySessionStore`, a `SettableRequestTelemetryFeature` per request, and `AuthorizeAsync`.
- Mutations (each one turned the project red): dropping the cookie manager failed 1, dropping the app/client binding 1, the client half alone 1, dropping the session_ref write 1, dropping the store 9, sliding on 1, default lifetime 1.

**Seams (chosen by implementer):**
1. A request through the framework's `UseAuthentication` over the services `AddPlatformIdentity` registers, against the test identity provider, using the `IdentityGateway` harness. This catches the real cookie and OIDC handler behaviour. It misses the composed pipeline order.
2. `ISessionStore`'s own interface, used for counting and reading sessions, with Platform.Testing's store behind a recorder.
3. `IRequestTelemetryFeature`, for `session_ref`.
4. The scheme's own `TicketDataFormat`, from `IOptionsMonitor`, to decrypt or forge cookies (S-B3, S-B5, S-B7, N-21).

**Decided by implementer:**
- `ISessionStore` is resolved from `HttpContext.RequestServices` when a session is first touched, not injected into the options setup. Nothing in production registers an `ISessionStore` until task 3.4. Constructor injection would therefore break every app-host request in the composed gateway, and with this choice only a request that presents or creates a session needs the store.
- `session_ref` is written whenever the adapter handles a key for the request (store, retrieve, renew, remove), including a key that resolves to no session for this app.
- A renew that loses the versioned replace race leaves the newer record and does not throw.
- A record bound to another app or client is treated as absent: not returned, renewed or removed.
- `AppBoundTicketStore` and `CallbackBlindCookieManager` are internal. `CookieOptionsSetup` is public, like `OidcOptionsSetup`.
- No rule id is written here. `auth.callback` and `auth.session` belong to the stages that answer (3.5, 3.9, ticket 56).
- A refused callback still surfaces as the framework's `AuthenticationFailureException` until 3.5's failure page.

### Standards (CODING_STANDARDS.md plus the smell baseline)
1. **Fixed: the code relied on vendor behaviour without citing the vendor.** `CallbackBlindCookieManager` stated two things about the framework without naming a source. First, that the OIDC handler reads its correlation and nonce cookies straight from `Request.Cookies`, which is the reason hiding the session cookie does not break the callback. Second, that its callback match uses case-insensitive `PathString` equality. I checked both against the aspnetcore v10.0.0 source: `RemoteAuthenticationHandler.ValidateCorrelationId` reads `Request.Cookies[cookieName]`, `ShouldHandleRequestAsync` compares `Options.CallbackPath == Request.Path`, and `OpenIdConnectHandler.ReadNonceCookie` walks `Request.Cookies.Keys`. The code now cites them. Only comments changed.
2. **Skipped: possible Duplicated Code.** `CookieOptionsSetup.Configure` and `OidcOptionsSetup.AppFor` each repeat a two-line check (`StartsWith(Prefix)` followed by `SchemeApp.Find`). The lookup that mattered is already shared in `SchemeApp`. Each setup owns its own prefix, and moving two lines into a shared method would add a parameter without removing any risk.
3. **Checked, no finding.** No comment refers to a stage by number. The comments cite their plan row, ADR or evidence id. The merge body states mutations, and the gate turned red under each one. No assertion I read was vacuous: the forged-cookie and planted-cookie tests each have a control that decrypts or authenticates.
