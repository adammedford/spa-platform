### Round 1

❓ **Q1** - **Ticket state**: The code for 1.2 is on main (#5, `5e2cbcc`), but the ticket still
says "not merged". Should the ticket be rewritten to say that the code is landed and that what
remains is (a) the exact-rule assertion in Q2, (b) the human apply and (c) P-06, which 6.9 runs at G3?

➡️ Yes. The remaining scope is that list, and the "Why this status" text is replaced with it.

---

❓ **Q2** - **Who proves "no other ingress rule"**: Row 1.2's done-when names this property, but
today only the resource-type allowlist covers it, and that allowlist accepts any number of rules.
The options are: (a) 1.2 adds a `terraform test` run that asserts exactly the four rules, with
their ports, protocols and referenced groups, and requires that no rule carries `cidr_ipv4` except
the task's 443 egress rule; (b) leave it to 1.9.

➡️ (a). It is 1.2's own done-when, the check costs nothing under ADR-0016's mock provider, and 1.9
can then reference it instead of restating it.

---

❓ **Q3** - **The VPC's default security group**: AWS creates a default group in every VPC, with an
allow-all ingress rule that refers to itself and an allow-all egress rule. Nothing in the module
attaches it, but it is an ingress rule in the cell's account, so "no other ingress rule" is false
when read literally against the deployed VPC. Should the module adopt it with
`aws_default_security_group` and declare no rules, which strips both?

➡️ Yes. It is free, it makes P-01 and P-06 true without a footnote, and it stops a later resource
that is created without a security group from inheriting allow-all. Network ACLs stay at the
default. The security groups are the boundary, as `docs/plan/01-plan.md` says in its trust table.

---

❓ **Q4** - **Zone selection**: `local.zones` takes the first two names that
`aws_availability_zones` returns for `state = "available"`. With the provider's defaults, that
result includes Local Zones the account has opted into. Should the data source filter on
`opt-in-status = opt-in-not-required`?

➡️ Yes. It is one filter block. Without it, opting into a Local Zone in us-east-1 could change
which subnets the plan places, and the ALB, Fargate ARM64 and ECS Exec are not offered in every
Local Zone.

---

❓ **Q5** - **The ALB and the task share subnets**: Because the task sits in the ALB's subnets, its
own ENI address is inside `TrustedNetworks`. A principal who can start a session on the task can
port-forward to the task's own address on 8080 and send `X-Forwarded-For` and `X-Forwarded-Proto`,
and stage 2 trusts both. The options are: (a) keep the plan's two shared public subnets and record
this as a Phase 1 gap; (b) add two more subnets so the ALB and the task are apart. Option (b) is
free in money, but it changes frozen plan row 1.2 ("two public subnets") and the P-01 counts.

➡️ (a). Only operators hold the tunnel, and they can already reach everything the task reaches.
The gap closes in Phase 2, which drops ECS Exec and moves tasks to private subnets.

---

❓ **Q6** - **Is the network part of the cell?**: The module creates a VPC for each instance, so a
Phase 2 cell would get its own VPC. The glossary's **Cell** omits the network. Should the cell be
defined to own its network, meaning its VPC, its subnets and its two security groups?

➡️ Yes for Phase 1, because that is what the code does and ADR-0012 calls a Phase 2 cell "one more
instance" of the module. Where a Phase 2 cell's network lives, for example on a corporate VPC, is
left to the P2 rows and does not block this ticket.

---

❓ **Q7** - **What the network deliberately leaves out in Phase 1**: The network has no VPC
endpoints (not even the free S3 gateway endpoint), no flow logs and no IPv6. Should all three stay
out?

➡️ Yes. The plan's topology sends the task's 443 out from a public address, an endpoint adds a
resource type that P-01 would have to allow, and P-06 is a timeout test that needs no flow logs.
The S3 gateway endpoint belongs with Phase 2's private subnets.

---

❓ **Q8** - **What to call the two security groups**: The row says "ALB group" and "task group", and
"task group" collides with ECS's task `group` attribute. Should prose, tests and glossary use
**task security group** and **ALB security group**, and avoid the bare "task group"?

➡️ Yes. The code already names them `aws_security_group.task` and `aws_security_group.alb`, and
`docs/plan/01-plan.md` already says "task security group".

## Decisions taken

Questions 2 to 5 and 7 to 10 are human-owned: the plan, contracts and ADRs say nothing on them. Adam
pre-accepted each recommendation on 2026-10-15 (overnight Q14 to Q22), and each is implemented as
recommended. The weighing is the implementer's, against `838cf97`. Questions 6 and 11 are the
integrator's to carry out and are not taken here.

1. **How "no other ingress rule" is proved (question 2).** Taken: (a) plan-time `terraform test`
   runs in the module's own test project. They read the rule names from the module source, because
   a plan cannot list every resource of a type, and then each rule's planned group, peer, protocol
   and ports. Cost: one test file, `tests/network.tftest.hcl`. It breaks nothing, and it is the
   shape ADR-0016 item 1 names for the security-group rules. (b) Leave it to row 1.9's root
   allowlist: free now, but row 1.2's own done-when stays unproven until 1.9 lands, and the type
   allowlist alone admits any number of rules. At `838cf97` a third rule, 8080 from `0.0.0.0/0`,
   passed every run (mutation M1 now fails it). (c) A credentialed plan read as JSON: it contradicts
   ADR-0016 items 1 and 3, so it is not available. (a) beats (b) because it proves the row's
   done-when now, and 1.9 can cite it rather than restate it. It would be wrong if a rule reached
   the deployed cell that the module source cannot show: one declared in the platform root, which
   is 1.9's root allowlist, or one added outside Terraform, which P-06 at G3 would catch. To
   reverse it, delete the test file; nothing in the module depends on it.
2. **The VPC's default security group (questions 3 and 9).** Taken: (a) adopt it as
   `aws_default_security_group.cell` with `ingress = []` and `egress = []`, add the type to the
   allowlist, and assert that it holds no rule. It costs no money. The first apply strips AWS's
   all-from-members ingress and all-out egress, and a rule added by hand later shows as drift.
   Nothing in the cell uses the group: the load balancer carries the ALB security group and the
   service the task security group, both already asserted. (b) Adopt it with the two lists
   omitted. The provider strips it at adoption all the same, but Terraform then "retains and
   ignores" existing rules (attributes-as-blocks), so a rule added by hand never shows in a plan.
   The planned value is also unknown, so no plan-time assertion can hold it (mutation D2). (c)
   Leave it unmanaged: free, but the account keeps an ingress rule (all traffic from the group's
   own members), so "no other ingress rule" is false read literally. A resource created later
   without a group would also inherit allow-all. (d) Restrict it with a network ACL instead: that
   adds `aws_network_acl` types and moves the boundary off the security groups, against
   `docs/plan/01-plan.md` -> Trust boundaries ("Task security group admits the ALB only"). (a) is
   the only option that makes the property true of the account, keeps it true, and can be proved
   at plan time. It would be wrong if something AWS creates in the VPC without a group needs the
   default group's access; the first apply's events or a broken resource would show it. To reverse
   it, delete the block. A destroy only drops it from state, and AWS's default rules do not come
   back on their own; restoring them means declaring them.
3. **Zone selection (question 4).** Taken: (a) filter on `opt-in-status = opt-in-not-required`.
   AWS says of `optInStatus`: "For Availability Zones, this parameter always has the value of
   `opt-in-not-required`", while Local and Wavelength Zones report `opted-in` or `not-opted-in`.
   (b) Filter on `zone-type = availability-zone`: equivalent today by the same API page, and also
   one block. (c) No filter: the provider sorts zones by name (`cmp.Compare` on `ZoneName` in the
   data source), so an opted-in Local Zone such as `us-east-1-bos-1a` sorts ahead of `us-east-1a`.
   It would take a subnet, and the next apply would replace the subnets, the load balancer and the
   task. (d) Pin the zones with a variable: robust, but it adds an input outside what
   `docs/plan/05-infrastructure-and-cost.md` says the module takes ("a cell name, an address range,
   a certificate, image digests and the issuer settings"). (a) beats (c) and (d) on those costs, and
   matches (b). It is the pre-accepted answer and the attribute the API defines Availability Zones
   by. It would be wrong if AWS added a zone kind that needs no opt-in yet cannot host an internal
   load balancer or Fargate. To reverse it, swap the filter: free before the first apply, a subnet
   replacement after it.
4. **The shared subnets (question 5).** Taken: (a) keep the plan's two shared public subnets, and
   record in `infra/modules/cell/README.md` the gap they leave: a Session Manager session holder can
   forge forwarded headers. (b) Add two more subnets so the load balancer and the task are apart:
   free in money, but it changes frozen plan row 1.2 ("two public subnets") and P-01's counts. (c)
   Narrow `TrustedNetworks` to the load balancer's node addresses: an ALB has no fixed addresses,
   so the gateway would stop trusting its own load balancer and break N-09. (a) wins: only
   operators hold the session, and they already reach the task's shell (threat T15), while (b)
   contradicts the frozen row and (c) breaks a test. It would be wrong if anyone but an operator
   gets `ssm:StartSession` on the task. To reverse it, take (b), which Phase 2 does anyway (P2-4
   private subnets, P2-9 no ECS Exec).
5. **What Phase 1 leaves out (question 7).** Taken: (a) no VPC endpoint, flow log or IPv6 range,
   now stated in the README. (b) Add the free S3 gateway endpoint: no charge, but it adds a
   resource type and route entries P-01 would have to allow, while the plan's topology sends 443
   out through the task's public address. (c) Add flow logs: they cost ingestion and add a log
   group and role, and P-06 is a timeout test that needs none. (a) keeps to the frozen topology in
   `docs/plan/05-infrastructure-and-cost.md`. It would be wrong if G3's P-06 run needs evidence of
   refused connections that only flow logs give. To reverse it, add them then.
6. **Vocabulary (question 8).** Taken: (a) "task security group" and "ALB security group" in every
   infra comment, test message, output and rule description, and in the ALB group's own
   description. (b) Change only comments and messages, and keep the bare term in the
   AWS-visible group description. That avoids a forced replacement of the group, but the
   replacement is free only before the first apply and an outage-prone swap of the load balancer's
   group after it. (a) takes the free moment: the roadmap shows S5 at 0 of 9, so nothing is
   applied. It would be wrong if the platform root had been applied, in which case revert that one
   string before the next apply.
7. **When 1.2 closes (question 10).** Taken: (a) close on green mock-provider tests. The apply
   rides the first deployment's Outstanding line, and P-06's deployed half stays with task 6.9.
   (b) Hold 1.2 open until an apply: the platform root applies the network together with 1.3, 1.4
   and 1.5, so applying 1.2 alone needs `-target`, and the row would wait on rows it does not own.
   Under ADR-0016 the done-when is a configuration property, so (a). It would be wrong if the first
   apply finds a network defect no plan shows, which is the class of the apostrophe descriptions
