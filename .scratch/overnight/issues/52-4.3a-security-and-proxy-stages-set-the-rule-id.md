# 52: 4.3a — The request gate, antiforgery and the proxy set their rule id on the telemetry feature
**Task:** 4.3a
**Owner:** ws4-proxy
**Blocked by:** None
**Status:** resolved

**What to build:** Four landed stages in `src/Platform.Security` and `src/Platform.Proxy` reject
requests and each writes its own Warning line with a `{Rule}` property. None of them can put the id
on the request log line. `IRequestTelemetryFeature` now exists in `src/Platform.Abstractions` for
exactly that (integrator's decision on change request 6.4, 14 October 2026).

| Rule ids | Where | From task | Stage |
| --- | --- | --- | --- |
| `path.invalid`, `path.reserved`, `gate.cookie-name`, `gate.fetch-site`, `gate.origin`, `gate.navigation`, `gate.method` | `src/Platform.Security/RequestGate.cs` | 4.3 | 6 |
| `csrf.token` | `src/Platform.Security/PlatformAntiforgery.cs` | 4.4 | 9 |
| `api.unknown` | `src/Platform.Proxy/UnknownApi.cs` | 4.1 | 10 |

**Not `src/Platform.Security/MethodAllowlist.cs`.** Task 4.6's stage-1 405 cannot use the feature:
`UsePlatformForwardedHeaders` installs the allowlist and `src/Gateway/Program.cs` calls that before
`app.UsePlatformTelemetry()`, so stage 2 has not created the feature and the request never reaches
stage 2 at all. A null-conditional write there is a permanent no-op. **Do not add one.** The gap is
ticket 53 and needs a gate. `RequestGate`'s own `gate.method` at stage 6 is in the table above and is
the one to write.

Write it null-conditionally, because a stage's own test project runs without stage 2:

```csharp
context.Features.Get<IRequestTelemetryFeature>()?.Rule = rule;
```

Each of these stages already computes the id for its own log line, so in most cases this is one line
beside an existing one.

Contracts: `contracts/request-gate.md` for the ids, `contracts/telemetry.md` -> "How `rule` and
`session_ref` reach the request line".

Three decisions already made, so they are not open here:

- **Every existing Warning line stays.** They carry which check and which header, which the request
  line does not, and `RequestGateTests` asserts on them.
- **Nothing here declares a `security.rejections` instrument.** Stage 2 counts it, from this same
  field. Six stages in three projects each declaring it would export several streams under different
  scopes.
- **Task 4.2's 401 leaves `Rule` null and gets no new id.** When no access token can be had, that 401
  reports the session's state; it is not a browser request that broke a rule, and
  `contracts/request-gate.md` has no id for it. Inventing one would change a G1a contract and would
  have to wait for a gate. That is the narrow case only: any 401 the table *does* give an id gets it.

## Acceptance
- [ ] Every id in the table is set on the feature by the stage that rejects under it
- [ ] `MethodAllowlist` is left alone, and nothing writes the feature from stage 1
- [ ] Every write is null-conditional, and each stage's own tests still pass with no feature installed
- [ ] A test per id asserts the stage set it, using `SettableRequestTelemetryFeature` from
      `Platform.Testing`. The assertion must be able to fail: a stage that sets the wrong id, or none,
      fails it
- [ ] The id on the feature and the id on the stage's own Warning line are the same value from the
      same source, not two literals that could drift
- [ ] No `security.rejections` instrument is created in either project
- [ ] `dotnet test --project tests/Platform.Security.Tests` and
      `dotnet test --project tests/Platform.Proxy.Tests` are green
- [ ] Writes only `src/Platform.Security`, `src/Platform.Proxy` and their two test projects
