### Standards axis

**1. The task role's "fails on widening" assertion did not fail on widening.** (Verified. Fixed.)

This is the ticket's own headline claim — acceptance box "the task role holds **no unrecognised
statement** — the test fails on widening, not only on absence", spec user stories 16 and 18, and the
reason the spec's Further Notes give for doing this work before the sitting at all.

Every assertion in `the_task_role_holds_no_unrecognised_statement` reads
`data.aws_iam_policy_document.task`. That is a closed account of the role's grants only while that
document is the whole of what the role holds, and it is not. Three declarations add a grant without
passing through it. Each was applied to `iam.tf` alone and left the suite **green at 25 of 25**:

| Mutation | Observed before the fix | After |
| --- | --- | --- |
| A second `aws_iam_role_policy` on `aws_iam_role.task`, granting `s3:DeleteObject` on `"*"` | 25 passed, 0 failed | 1 of 26 failed |
| `managed_policy_arns = ["arn:aws:iam::aws:policy/AdministratorAccess"]` on `aws_iam_role.task` | 25 passed, 0 failed | 1 of 26 failed |
| An `inline_policy` block on `aws_iam_role.task` | 25 passed, 0 failed | 1 of 26 failed |

The resource-type allowlist does not catch the first, because `aws_iam_role_policy` is already a
named type. It does catch `aws_iam_role_policy_attachment`, which is why that one needs nothing.

The Comments' own "mis-aimed mutation" note is where this was missed: the separate policy document
was correctly found not to widen the role *while nothing attached it*, and the mutation was then

teardown role, so the uncaught grant was the one the ticket's own Comments say was kept out.

Fixed in `tests/module.tftest.hcl` with three assertions in that run: the set of
`aws_iam_role_policy` declarations is exactly `task` and `task_execution`; no `managed_policy_arns`
or `inline_policy` is declared anywhere in the module; and each policy is bound to its own role.
The first two read the module's source rather than a value, because `managed_policy_arns` and
`inline_policy` are Optional+Computed in provider v6 and so read as *unknown* at plan time when
correctly unset — an assertion on their value could not pass cleanly. That is the same reason the
resource-type allowlist and the no-default check already read source.

### Spec axis

**3. `ForwardedHeaders:TrustedNetworks` was the whole VPC range, not the ALB subnets.** (Verified.
Fixed.)

`contracts/platform-config.schema.json` names this field's value in its own words: "The ALB subnets,
in CIDR form." `ecs.tf` supplied `var.vpc_cidr`. Only two subnets of that range are allocated
(`cidrsubnet` in `network.tf`), so stage 1 trusted `X-Forwarded-For` and `X-Forwarded-Proto` from
every unallocated address in the cell as well as from the load balancer — wider than the contract
specifies, and wider than N-09's intent.

The assertion could not catch it, because it compared the environment against `var.vpc_cidr`: the
guard restated the value it was protecting, which `CODING_STANDARDS.md` → "A guard reads the thing
it guards" is about. Acceptance box "the trusted-network setting names this cell's network only" was
literally satisfied, which is why this is a spec-axis finding rather than a plain defect — the
contract is narrower than the box.

Fixed by rendering one entry per subnet the load balancer sits in, from `aws_subnet.public`, which
is the same expression `alb.tf` uses for the ALB's own subnets. The run now reads the expected value
off `aws_lb.cell.subnets` instead of a variable, and adds the anti-widening half. Mutations: the old
`var.vpc_cidr` form fails 3 of the run's assertions; dropping one subnet's entry fails 2.
