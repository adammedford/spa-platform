# 48: 4.1a — Pin the largest `timeoutSeconds` the proxy applies, by test
**Task:** 4.1a
**Owner:** ws4-proxy
**Blocked by:** None
**Status:** ready-for-agent

**What to build:** A test in `tests/Platform.Proxy.Tests` that pins the largest `apis[].timeoutSeconds`
YARP applies exactly, so the number lives in CI rather than in a decision document or a comment.

`RegistryProxyConfig` passes `api.Timeout` to YARP as `ForwarderRequestConfig.ActivityTimeout`. The
integrator ran this on 14 October 2026 against .NET 10.0.12 and YARP 2.3.0, outside the repository:

- YARP's `ActivityCancellationTokenSource` holds the activity timeout in an `Int32` of milliseconds
  and **saturates** at `Int32.MaxValue`. At 2,147,483 seconds the stored value is exact
  (2,147,483,000 ms). At 2,147,484 and at every larger value tried, including the validator's present
  bound of 922,337,203,685 seconds, the stored value is 2,147,483,647 ms.
- Nothing throws. `IConfigValidator.ValidateClusterAsync` accepted every value tried, and a real
  forward through `IHttpForwarder` returned 200 at every one.
- `CancellationTokenSource.CancelAfter(TimeSpan)` on .NET 10.0.12 accepts up to `UInt32.MaxValue - 1`
  milliseconds, so 4,294,967 seconds, and throws above it. YARP clamps first, so that ceiling is
  never reached.

So the defect is silence, not an exception: above **2,147,483 seconds** (24.855 days) the registry
says one thing and the proxy applies another, with no error and no log. The grilling expected an
`ArgumentOutOfRangeException` from `CancelAfter`; that prediction is wrong, and the test should assert
the clamp, not an exception.

## Acceptance

- [ ] The test fails if a YARP or .NET upgrade moves the ceiling, and says so when it fails
