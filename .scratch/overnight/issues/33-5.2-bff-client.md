## Answer
**What landed** (branch `task/5.2-bff-client`, commit 85b4a4e, forked from da18371):
- `fixtures/bff-client.js`: a plain script that adds `window.BffClient` with `session()`, `api(path, init)`, `login(returnUrl)` and `logout()`. `session()` resolves to `{sub, name, email, expiresAt}`, or to null on a 401, and keeps `csrfToken` in a closure. `api()` adds `X-CSRF-TOKEN` to unsafe methods only. It reads the session first if no token has been read yet. It rejects any path that does not resolve to `/api/**` on its own origin. On either 401 it starts a login back to the current page. `login()` navigates to `/bff/login`, and a returnUrl that is not a local path becomes `/`. `logout()` submits a form POST to `/bff/logout` that has no fields.
- `fixtures/Fixtures.Tests/HeadlessBrowser.cs`: installs Chromium once per run with `Microsoft.Playwright.Program.Main(["install","chromium"])`, so PowerShell is not needed, then starts headless Chromium.
- `fixtures/Fixtures.Tests/BffClientPage.cs`: a page on `https://app1.test` where `page.RouteAsync` answers every request. It records every request.
- `fixtures/Fixtures.Tests/BffClientTests.cs`: 25 cases. The tests read the header name, the session field, the safe methods and the 401 codes from `contracts/http-contract.md`. A mutation run (session returning the token, returnUrl unchecked, the token on every method, logout as GET) failed 9 cases, so the assertions can fail.
- `Fixtures.Tests.csproj`: `<PackageReference Include="Microsoft.Playwright" />`. The version is already pinned centrally.

**Seams (chosen by implementer):** the public surface of `window.BffClient`. Each test observes it through the requests it makes (method, headers, post data, whether it is a navigation) and through the navigations it starts.

**Decided by implementer:**
- The client is a plain IIFE script with one global, not an ES module, because there is no build step and it loads with `<script src>`.
- `session()` resolves to null on a 401 and does not navigate. The SPA decides whether to log in.
- `api()` resolves with the Response whatever its status. On a 401 it also starts the login navigation. A 403 `csrf_failed` is left to the caller.
- `api()` refuses any path that does not resolve to `/api/**` on its own origin. It rejects with a TypeError, as fetch does, so the token never leaves `/api`.
- With no argument, `login()` returns to the current pathname, search and hash.
- The 5.1 SPAs' scripts are unchanged. They inline the same behaviour, and switching them to bff-client.js would rename their hashed assets and widen the scope.

**Gate:** GREEN, with total 617, failed 0, succeeded 617 (`.scratch/overnight/log/5.2-implement.txt`).

**Risk, not blocking:** this Mac had Chromium build 1243 cached, so the browser installer did nothing here. Nobody has tried it on CI's Linux runner, where it will download the browser. Run it there before relying on it.

- **No finding:** session fetch, the CSRF header on unsafe methods only, both 401 codes leading to a fresh login, login as a navigation and logout as a form POST all match the contract rows. The scope stayed inside `fixtures/` (A-05 passed).
