# 49: 2.1b — The validator refuses a `timeoutSeconds` the proxy cannot apply
**Task:** 2.1b
**Owner:** ws2-hosting
**Blocked by:** MR-1 (see Comments; ticket 48 has landed)
**Status:** blocked

**What to build:** `RegistryValidator.MaximumTimeoutSeconds` is
`TimeSpan.MaxValue.Ticks / TimeSpan.TicksPerSecond`, 922,337,203,685. That is the largest value the
*model* can hold. It is about 430,000 times larger than the largest value the *proxy* applies, which
ticket 48 pins by test. Between the two, a document validates, goes live, and the proxy silently
applies a different idle limit from the one the registry states.

Narrow the bound to the proxy's, reported under the existing `integer-out-of-range` id.

Contracts: `contracts/README.md` -> "Rules that JSON Schema cannot express", the row "A schema-valid
integer the platform cannot hold or apply", and the `timeoutSeconds` bullet below the table. Both were
written for this (change request 2.1, decided 14 October 2026). `registry.schema.json` stays unbounded
above: the limit is the runtime's, so a runtime upgrade must not become a contract change.

## Acceptance
- [ ] `timeoutSeconds` at the ceiling validates; one second above it is reported as
      `integer-out-of-range` with a message that names the ceiling and why
- [ ] `revision` beyond Int64 is still reported under the same id, unchanged

- [ ] `dotnet test --project tests/Platform.Registry.Tests` is green
- [ ] Writes only `src/Platform.Registry` and `tests/Platform.Registry.Tests`

## Comments

**2026-10-14, integrator.** This ticket's blocker changed. Ticket 48 has landed the measured number
(`ProxyTimeout.MaximumTimeoutSeconds = 2_147_483`, PR #21), so the stated blocker is satisfied — but
the real one is not, and it is not 48.

ADR-0015 decided that the proxy's constant **stays in `Platform.Proxy`**: it is measured from a pinned
YARP 2.3.0 on .NET 10.0.12, and `Platform.Abstractions` must not carry a number whose truth depends on
a dependency version. A-03 therefore still stops `Platform.Registry` from reading it, so this ticket
cannot simply reference the constant.

The decided shape instead: **the contract states the bound and the proxy proves it.**
`contracts/registry.schema.json` gives `timeoutSeconds` a `maximum`, this validator refuses anything
above it under the existing `integer-out-of-range` id, and task 4.1a's test asserts YARP can still
apply the contracted bound.

That is deferred, with its condition written down: `registry.schema.json:162` says "the plan states no
upper bound", so adding a `maximum` changes a frozen schema and raises the `schemaVersion` question
that gap **MR-1** in `docs/roadmap.md` says nothing yet answers — no rule states which registry
documents a given gateway build accepts. **This ticket lands with MR-1, not before it.**

Until then the validator keeps `MaximumTimeoutSeconds = TimeSpan.MaxValue.Ticks / TimeSpan.TicksPerSecond`,
which is wrong by a factor of about 430,000 but wrong in the safe direction: it refuses nothing the
proxy would have applied correctly. The exposure is unchanged from today — a document can state a
timeout the proxy silently clamps — and it is recorded here rather than in the code.

**Status: blocked** (was `ready-for-agent`), on MR-1.
