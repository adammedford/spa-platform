### Standards (CODING_STANDARDS.md plus the smell baseline)

1. **Vendor rule with no citation, fixed.** `idp-cognito/variables.tf` refused domain prefixes containing aws, amazon or cognito, and its regex was a prefix pattern, but neither cited a source. I checked both against the vendor. The pattern matches CreateUserPoolDomain's `Domain` pattern, `^[a-z0-9](?:[a-z0-9\-]{0,61}[a-z0-9])?$`. The reserved words are under "Reserved terms" in the developer guide's `cognito-user-pools-assign-domain.html`. The page `main.tf` cites (`assign-domain-prefix.html`) does not state them. I added both URLs.
2. **A comment claimed more than its test proves, fixed.** The module's `issuer_and_domain_feed_the_outputs_contract` said its literals came "from contracts/infra-outputs.example.json". In fact the expected strings follow from the run's own overrides, so the run proves how the module builds the values, not that they agree with the contract. Reading the example file would add little, because the override fixes the endpoint anyway. I rewrote the comment to say what the run proves. "A guard reads the thing it guards" does not apply here, because the thing guarded is the module's string construction.
3. **Root tags test checks `local.tags`, not that `default_tags` consumes it. Not fixed (known limit).** A mock provider does not run the AWS provider's tag merge, so `tags_all` under a mock would be invented, not proof. The contract half of the test does read `contracts/resource-tags.md`. I verified it can fail: with `Platform` set to `spa-platform-bootstrap`, the root test reported "2 passed, 1 failed", and the file was reverted.
4. **Judgement only, not acted on.** `password_length` and the `user_pool_arn` output are possible Speculative Generality. Both are small and harmless, and 1.8 may want the ARN.
5. **Vendor claims checked and left as they are.** Essentials: the feature-plans page says "Managed login is available in the Essentials and Plus tiers", so the `ESSENTIALS` comment holds. `password` on `aws_cognito_user` sets a permanent password. The README's discovery URL `<issuer>/.well-known/openid-configuration` matches the guide's "Discovery endpoints are on a different domain".

### Spec (ticket, plan row 1.1, contracts/resource-tags.md, contracts/infra-outputs.schema.json)

1. **Plan role could not refresh the test users, fixed.** The provider's `aws_cognito_user` read calls only `AdminGetUser` (`internal/service/cognitoidp/user.go`, `findUserByTwoPartKey`). The bootstrap's read-only CI plan role had `ListUsers` but not `AdminGetUser`, so any CI plan of this root after the apply would fail with AccessDenied on each user. I added `cognito-idp:AdminGetUser` to `DescribeIdentityProvider` in `infra/bootstrap/ci-role.tf`, with a comment that cites the provider source. This widens the role by one action. That is justified because the action is read-only and returns attributes, never a password. No `kms:` grant is needed for the SecureString reads, because `alias/aws/ssm` is AWS-managed and its key policy allows decryption through SSM. **If task 1.0's bootstrap has already been applied in the account, it needs a re-apply to pick this up.** That is added to Outstanding (human).
2. **Everything else the spec asks for is present, and I verified it by reading the code and running the tests.** It covers Essentials, a prefix domain with `managed_login_version = 2`, resource servers and users read from `fixtures/cognito/pool.json`, and no app clients. Passwords go into SecureString parameters at `/spa-platform/<cell>/test-users/<user>`, and no output carries them. Tags are set through `default_tags`, and the untaggable children (the domain, resource servers and users) belong to the tagged pool. The backend is partial S3 with `use_lockfile` and key `poc/idp/terraform.tfstate`, matching `infra/bootstrap/outputs.tf`. Terraform must be >= 1.11. Outputs are named for `infra-outputs.schema.json`. I ran `terraform test` myself: the module gives 8 passed, 0 failed, and the root gives 3 passed, 0 failed.
