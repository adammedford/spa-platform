## Answer

**Landed** on `task/3.6-options-invalidator` (commit `6ae668d`, forked from `overnight/2026-10-16` at `f14f90f`).

- `src/Platform.Identity/OptionsInvalidator.cs`: subscribes to `IRegistry.OnSwapped` (so it runs after the swap), and for every entry whose `Fingerprint` changed or disappeared evicts `cookie:{app}` and `oidc:{app}` from the options caches; it purges the app's sessions (`ISessionStore.RemoveAppAsync`) only when the entry went or names a new client. A rotated secret or a release change keeps the sessions. Logs app id, reason and revision only (event ids 3601 to 3603).
- `src/Platform.Identity/AppOptionsCache.cs`: replaces the framework's `OptionsCache<T>` for both scheme kinds. A build that threw is removed before its exception leaves (R-D10), and each entry remembers the fingerprint it was built from: options built for a request pinned to a replaced entry are served to that request but never cached.
- `PlatformIdentityExtensions.AddPlatformIdentity` registers both; `OidcOptionsSetup` and `CookieOptionsSetup` take the invalidator as a dependency so it has subscribed before the first options exist.
- Tests: `tests/Platform.Identity.Tests/OptionsInvalidatorTests.cs` (10 tests); `IdentityGateway` gained `SwapAsync`, `Registry`, `Secrets`, a pinned-snapshot argument, and a 404 stand-in for host resolution when the pinned snapshot lacks the host.

**Proven:** S-D1/R-C1 (onboard, 404 before, login after, app 1's instance untouched), S-D2 (same instance across the swap), S-D3/R-C2 (stale secret refused `invalid_client`, new secret after swap, session survives), S-D4/R-C3 (login across a rebuild), S-D5/R-C4 (code refused `invalid_grant` for the new client, no custom guard), S-D6/N-22 (old-client session 401 and purged), S-D7/R-C5 (removed host and callback 404, sessions purged, in-flight pinned request 401, other app unaffected), R-D10 (failed build rebuilt on next read, no swap), F-09 identity half (rotate and remove in one swap).

**Mutations** (each reverted): no eviction failed 1 of 96; no purge 3; purge on every change 2; keep faulted build 1; ignore fingerprint 1; framework cache instead of `AppOptionsCache` 2.

**Seams (chosen by implementer):** a request through the framework's `UseAuthentication` in `IdentityGateway`; `IOptionsMonitor<T>.Get(name)` and `IOptionsMonitorCache<T>.TryAdd` (the framework's own interfaces) for instance identity and eviction; `ISessionStore` for the purge; `InMemoryRegistry.Swap` as the registry.

**Decided by implementer:**
- Purge only on removal or a client-id change; a rotated secret (same client) keeps sessions, per S-D3.
- The purge is waited for synchronously inside the `OnSwapped` callback (the callback is synchronous; it runs on the swapping thread, never a request); a failed purge is logged and does not stop other apps' eviction.
- A fingerprint-tagged options cache closes the window where a request pinned before a swap builds after the eviction and would leave the old entry's options cached.
- The invalidator is constructed through the options setups' dependency rather than a hosted service, so it works without a started host.

**Gate:** GREEN (`.scratch/overnight/log/3.6-implement.txt`): `total: 1339 failed: 0 succeeded: 1339`.

### Standards

- **Fixed: the failed-purge path had no test.** `OptionsInvalidator.Purge` catches and logs a store failure and the Answer claims it "does not stop other apps' eviction", but no test exercised it. Added `A_purge_that_fails_leaves_the_swap_standing_and_the_other_apps_evicted_and_purged` with a `FailingPurgeStore`. Mutation: inverting the catch filter (letting the failure escape) failed 1 of 97; reverted.
- **Skipped (judgement): `_ = invalidator;` in both options setups.** An unusual way to force construction, but it is commented with its reason and plan row, and the alternative (a hosted service) would not run without a started host, as the Answer notes.
- **Skipped: the 404 assertions in S-D1/S-D7 tests are answered by the harness** (`IdentityGateway.SendAsync` returns 404 when the pinned snapshot lacks the host), so they cannot fail on identity code. The test comments say so; the 404 is host resolution's (task 2.3), outside this row's identity half. The identity assertions beside them (purge, pinned 401, options rebuilt) can fail, per the stated mutations.
- **Skipped: "Evicted" log line also fires for an onboarded app** (before is null), where nothing was evicted. Harmless; logs app id and revision only (N-16 safe).
- Comments cite rows and evidence ids, vendor behaviour cites `OptionsCache.cs` at v10.0.0, path ownership passes (A-05).

### Spec

- All five acceptance lines checked against `docs/plan/07-evidence.md` and `04-tests.md`; each has a test that asserts the identity behaviour. Boxes stay ticked.
- **Fixed: `AppOptionsCache.GetOrAdd` could serve a cached entry built for a different fingerprint.** When `TryGetValue` misses (or `TryUpdate` loses), the fallback `entries.GetOrAdd(name, fresh)` returns whatever another thread put there, which can be an entry built by a request pinned just before a swap; it was served without the fingerprint check that the class's own doc promises ("served only to a request pinned to the fingerprint it was built from"). Now the chosen entry is re-checked and, on a mismatch, this request gets its own uncached build. Found by reading; the race needs two threads interleaving inside one call, so it has no deterministic test.
- **Fixed: one app's purge delayed another app's eviction.** The purge (synchronous wait on the session store) ran inside the per-app loop, so a slow store held later apps' stale options in the cache. Evictions now all happen first, then the purges. Latency only; no test asserts ordering.
- No scope creep: `AppOptionsCache` is what makes R-D10 stop reproducing and is within the row.
