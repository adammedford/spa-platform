## Proposed glossary / ADR

### Glossary (proposed, not applied)

- **Rejection**: the gateway ending a request because the request broke a platform rule, answered with the browser contract's error `code` and logged and counted under a rule id. A rejection is the gateway's. An upstream API's 4xx is not one, and neither is a 401 that reports the session's state. *Avoid* "refusal" in contracts. (Q17)
- **Rule id**: the stable name of the rule behind a rejection, such as `gate.fetch-site` or `host.unknown`, from the table in `contracts/request-gate.md`. It appears as `rule` on the request line and as a tag on `security.rejections`. Distinct from the response's `code`, which "says little on purpose". *Avoid* "reason" and "error code" for it.
- **Request line**: the one JSON log line the gateway writes for each request, after the rest of the pipeline has returned, carrying the fields in `contracts/telemetry.md`. Distinct from an **event line** (login, refresh, logout, registry swap) and from a stage's own diagnostic lines.

### ADR candidates

None. The feature (Q1) is a real trade-off and becomes harder to reverse once six stages write it, but it is not surprising: it is the framework's own idiom, and `IAppFeature` already uses it, so criterion 2 fails. Counting in stage 2 (Q3) is reversible inside one project (criterion 1 fails). The between-gates rule (Q14) is a process rule, and it belongs in `contracts/README.md` beside the freeze it qualifies, not in an architecture decision record.
