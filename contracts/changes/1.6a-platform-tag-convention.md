# Change request 1.6a: write down the platform tag

- **Raised by:** workstream 1, AWS and IaC
- **Tasks:** 1.0 and 1.6a, and anything later that tags an AWS resource
- **Date:** 2026-10-12
- **Status:** decided, 2026-10-12. See the Decision section at the bottom, ADR-0013 and `contracts/resource-tags.md`.

## What is missing

The plan names "the platform tag" three times and never says what it is.

- `docs/plan/05-infrastructure-and-cost.md`, Teardown: `teardown.sh` "queries for
  the platform tag. Any resource still tagged fails the script."
- `docs/plan/04-tests.md`, P-05: "A query for the platform tag returns no
  resources."
- `docs/plan/03-workstreams-and-tasks.md`, task 1.6a: the certificate is
  "imported to ACM under the platform tag".

Three owners have to agree on the same string or the check is vacuous.
Workstream 1 applies the tag (every root, and `certs.sh`), workstream 1 queries
it (`teardown.sh`, task 1.7), and workstream 6 asserts on the query (P-05, and
the G3 teardown-and-redeploy). A tag that P-05 queries under a different key
than the roots apply would pass while leaving the account full of resources.

## What tasks 1.0 and 1.6a implemented

Written down here so the integrator can confirm or correct it before task 1.7
and task 6.x are written against it.

| Tag | Value | On |
| --- | --- | --- |
| `Platform` | `spa-platform` | Every resource in `envs/poc/{idp,apps,platform}`, and the certificate `certs.sh` imports |
| `Cell` | the cell name, e.g. `poc` | The same resources |
| `ManagedBy` | `terraform`, or `certs.sh` | The same resources |

`Platform = spa-platform` is the platform tag: the one `teardown.sh` queries and
P-05 asserts returns nothing.

### The bootstrap exemption

Resources in `infra/bootstrap` carry `Platform = spa-platform-bootstrap`
instead, plus `Cell`, `Component = bootstrap` and `Root`.

This is deliberate. The state bucket and the CI plan role outlive every
teardown: the plan says teardown "destroys the three roots in reverse order"
and "the state bucket goes last, by hand". If those two answered the platform
query, P-05 could never pass, and a `teardown.sh` that deleted them would
destroy the state of the roots it is in the middle of destroying.

The alternative — one `Platform` value for everything, and a `teardown.sh`
query that excludes the two bootstrap resources by ARN — was rejected because
it puts the exemption in the script that is trying to prove the account is
empty, which is the wrong place for it.

## Decision asked for

1. Confirm `Platform = spa-platform` as the platform tag, or name another value.
2. Confirm the bootstrap exemption, or say how else P-05 should coexist with two
   resources that are meant to survive teardown.
3. Say where it should be recorded, so that workstream 6 can read it rather than
   infer it. Workstream 1 suggests the infrastructure outputs contract
   (`contracts/infra-outputs.schema.json`, task I-2), which workstreams 1 and 6
   already propose jointly, or a short section in `docs/plan/02-contracts.md`.

Nothing is blocked meanwhile: tasks 1.0 and 1.6a tag as above, and a change of
value is a one-line edit in `local.tags` per root and in `PLATFORM_TAG_VALUE` in
`tools/scripts/certs.sh`.

---

## Decision

Integrator, 2026-10-12. All three questions answered as asked, nothing to change in the code tasks
1.0 and 1.6a already wrote.

1. **Confirmed: `Platform = spa-platform` is the platform tag**, with `Cell` and `ManagedBy`
   alongside it, exactly as the table above has it.
2. **Confirmed: the bootstrap exemption**, with `Platform = spa-platform-bootstrap` plus `Cell`,
   `Component` and `Root`. The reasoning in this request is right, and the rejected
   alternative — one value for everything plus an ARN exclusion list inside `teardown.sh` — is
   rejected here for the reason given: it puts the exemption inside the script that is trying to
   prove the account is empty.
3. **Recorded in a new contract file, `contracts/resource-tags.md`**, not in the infrastructure
   outputs contract. `outputs.json` is written after an apply, but `certs.sh` needs the tag before
   any root runs and teardown needs it when outputs may be stale or gone, so reading a teardown
   constant out of an apply artefact is circular. `docs/plan/02-contracts.md` was not an option
   either: the plan is a frozen export and is never edited in place.

The decision record is [ADR-0013](../../docs/adr/0013-platform-tag-and-bootstrap-exemption.md).

### Two things added on top of what was asked

- **The query is an exact value match.** No prefix match, no wildcard, no `contains`. The two
  `Platform` values share their first eleven characters, so a `Values=spa-platform*` query would
  sweep up the state bucket and the CI plan role and teardown would fail on every run. The tagging
  API's `--tag-filters` form is already exact; the rule is written down so nobody hand-rolls
  something looser.
- **Untaggable resources need a tagged parent.** Cognito app clients, resource servers and
  managed-login branding styles accept no tags, which is most of what the apps root creates. P-05
  still holds because each is a child of the tagged user pool and dies with it. That is now a stated
  rule in the contract: a root that adds an untaggable resource with no tagged parent makes P-05
  vacuous for it and files a change request instead.

Nothing is blocked. Tasks 1.0 and 1.6a are unblocked and tag as they already do.
