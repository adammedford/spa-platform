- **Status:** decided, 2026-10-16. See the Decision section below.

## 1. Three illustrative values need to follow the proposed bucket-name convention

The proposed default is `spa-platform-<cell>-<account id>`; current Terraform at `070e3fae` still
defaults to `spa-platform-<cell>` and supports a `bucket_name` override. The account id is proposed
because an S3 bucket name is global, so a second account applying the same cell would otherwise collide, and
because the managed-login prefix already carries it for the same reason.

Three illustrative values in two contracts frozen at G1a still read `spa-platform-poc`:

- `contracts/infra-outputs.example.json` → `bucket`
- `contracts/platform-config.example.json` → `Registry.Bucket` and `Assets.Bucket`

These are examples, not schema: the `bucketName` definition they reference is a pattern that both
forms satisfy, so nothing fails today. They matter because they are the only rendered instance of the
name anywhere in the contracts. ADR-0014's draft used `spa-platform-<cell>-*`, which misses the
current unsuffixed default but matches the proposed account-qualified name. The final grant must
use the actual bucket ARN. Examples should follow the convention once workstream 1 implements it.

**Asked for:** update the three values to `spa-platform-poc-111122223333`, matching the placeholder
account id the identity module's test file already uses, so every rendered example of the name agrees
with the resource.

This is prose-level, not a schema narrowing, so `contracts/README.md` allows it to land between
gates.

## 2. ADR-0009 rejects no alternative that a reader would reach for first

ADR-0009's Alternatives rejected table has one row, a mutable "current" prefix. The obvious
alternative to a bucket policy for write-once objects is **S3 Object Lock**, and the ADR does not
mention it. A reader asking "why is immutability enforced by a policy we have to get right, rather
than by the feature designed for it?" finds no answer, and the honest answer is a constraint worth
recording rather than a preference:

- Object Lock requires versioning and can be enabled on an existing bucket. Once enabled, it cannot
  be disabled and versioning cannot be suspended; see AWS's
  [configuration guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-configure.html),
  checked 15 October 2026. Bucket replacement is not a reason to reject it;
- in compliance mode nothing can delete an object before its retention expires, including the
  teardown role, which would make P-05 ("a query for the platform tag returns no resources")
  unreachable for the length of the retention;
- in governance mode the bypass permission becomes the thing that has to be scoped correctly, which
  is the problem the bucket policy already solves, with one more moving part.

**Asked for:** one row in ADR-0009's Alternatives rejected table recording that, and a pointer to
ADR-0014 for who holds the delete.

## Decision

Decided on the overnight grilling of ticket 65 (Q1–Q12), whose recommendations Adam accepted on
2026-10-16. It goes further than the request asked, because the grilling found the request's own
account-qualified name does not do what it was for.

1. **The platform bucket's default is `spa-platform-<cell>-<account id>-<region>-an`, in S3's
   account regional namespace** (Q1). A name that is only account-*qualified* in the global
   namespace can still be created first by another account, since an account id is not a secret,
   and task 6.9 tears down and redeploys. The regional namespace is the one form nobody else can
   create. The pinned `hashicorp/aws` 6.68.0 carries a `bucket_namespace` argument and the
   `account-regional` value (checked in the provider binary on 2026-10-16), so workstream 1 can set
   it. Require the explicit namespace argument: a formatted name alone does not opt in.
   Sources: [AWS namespace rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/gpbucketnamespaces.html)
   and the [pinned provider resource](https://github.com/hashicorp/terraform-provider-aws/blob/v6.68.0/website/docs/r/s3_bucket.html.markdown).
   An unsupported Region (currently Bahrain and UAE) or provider is a deployment prerequisite to
   resolve, not a silent downgrade to a globally claimable bucket name.
2. **`bucket_name` stays as an override; empty means the convention** (Q2). **Every consumer reads
   the platform root's `bucket` output, never derives the name**, and `teardown.sh` reads it from
   state (Q3). `contracts/s3-layout.md` now says so (Q7).
3. **The examples follow the resources** (Q4, Q5): both example files render the bucket as
   `spa-platform-poc-111122223333-us-east-1-an` and the Cognito domain as the idp root's own default,
   which the examples contradicted as well.
4. **The 63-character limit is a plan-time precondition in `modules/cell`**, not a narrower cell
   bound (Q6): a 22-character cell fits in `us-east-2` and not in a 14-character Region.
5. **ADR-0009 gains the Object Lock row, amended in place** (Q8, Q9), led by the finding that Object
   Lock protects versions, not keys.
6. **The state bucket stays in the global namespace** (Q11): it is applied, holds every root's state,
   and already carries the account id. Q12 does not arise under the regional form.

**Workstream 1's follow-ups (Q10)**, folded into tasks 1.5 and 1.7 rather than a new ticket: the
namespaced default from the existing account and Region data sources, the `bucket_name` description,
the length precondition, a module test of the default name, and `teardown.sh` reading `bucket` from
the platform root's state. Every one lands before the first platform-root apply.
