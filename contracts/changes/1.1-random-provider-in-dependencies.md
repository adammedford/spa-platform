- **Raised by:** workstream 1, AWS and IaC

- **Date:** 2026-10-13

## What changed

Task 1.1 generates the test-user passwords. It does so with the `random_password` resource from
the `hashicorp/random` provider, so the identity root and `infra/modules/idp-cognito` now require
a second provider beside `hashicorp/aws`. Both lock files (`.terraform.lock.hcl` in each
directory) are committed and pin it.

`docs/dependencies.md` -> Terraform lists only the CLI and `hashicorp/aws`. It is the integrator's
file, so this request asks for one row:

| Item | Version | Note |
| --- | --- | --- |
| Provider `hashicorp/random` | 3.9.1 | Constrain to `~> 3.7`. MPL-2.0, published by HashiCorp. Task 1.1's test-user passwords |

Checked on 13 October 2026 against the Terraform registry by `terraform init`, which resolved
`~> 3.7` to 3.9.1.

## Why this provider and not the AWS one

The password has to be generated once and stay stable, because `aws_cognito_user`'s `password`
in `hashicorp/aws` 6.68.0 is an ordinary sensitive attribute, not a write-only one (checked with
`terraform providers schema -json`). So:

- An ephemeral generator (`random_password` as an ephemeral resource, or the AWS provider's
  `aws_secretsmanager_random_password`) cannot feed it: Terraform refuses an ephemeral value in a
  non-write-only attribute.
- The `aws_secretsmanager_random_password` data source returns a new value on every plan, so every
  plan would change both the user and the parameter. It also needs
  `secretsmanager:GetRandomPassword`, which the CI plan role does not have.

`random_password` as a managed resource generates once and keeps the value in state, which is
encrypted, private and TLS only (`infra/bootstrap/state.tf`). The password is in state either way,
because the Cognito user resource stores it.

## What it does not change

No contract and no output. The password is never an output; the outputs name the parameter only,
as `contracts/infra-outputs.schema.json` -> `testUsers` requires.
