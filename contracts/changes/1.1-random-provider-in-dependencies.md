# Change request 1.1: record the `hashicorp/random` provider in `docs/dependencies.md`

- **Raised by:** workstream 1, AWS and IaC
- **Tasks:** 1.1, and 1.8 if it generates anything
- **Date:** 2026-10-13
- **Status:** decided, 2026-10-14. See the Decision section below.

## What changed

Task 1.1 generates the test-user passwords. It does so with the `random_password` resource from
the `hashicorp/random` provider, so the identity root and `infra/modules/idp-cognito` now require
a second provider beside `hashicorp/aws`. Both lock files (`.terraform.lock.hcl` in each
directory) are committed and pin it.

`docs/dependencies.md` -> Terraform lists only the CLI and `hashicorp/aws`. It is the integrator's
file, so this request asks for one row:

| Item | Version | Note |
| --- | --- | --- |
| Provider `hashicorp/random` | 3.9.1 | Constrain to `~> 3.7`. MPL-2.0, published by HashiCorp. Task 1.1's test-user passwords |

Checked on 13 October 2026 against the Terraform registry by `terraform init`, which resolved
`~> 3.7` to 3.9.1.

## Why this provider and not the AWS one

The password has to be generated once and stay stable, because `aws_cognito_user`'s `password`
in `hashicorp/aws` 6.68.0 is an ordinary sensitive attribute, not a write-only one (checked with
`terraform providers schema -json`). So:

- An ephemeral generator (`random_password` as an ephemeral resource, or the AWS provider's
  `aws_secretsmanager_random_password`) cannot feed it: Terraform refuses an ephemeral value in a
  non-write-only attribute.
- The `aws_secretsmanager_random_password` data source returns a new value on every plan, so every
  plan would change both the user and the parameter. It also needs
  `secretsmanager:GetRandomPassword`, which the CI plan role does not have.

`random_password` as a managed resource generates once and keeps the value in state, which is
encrypted, private and TLS only (`infra/bootstrap/state.tf`). The password is in state either way,
because the Cognito user resource stores it.

## What it does not change

No contract and no output. The password is never an output; the outputs name the parameter only,
as `contracts/infra-outputs.schema.json` -> `testUsers` requires.

## Decision

Integrator, 2026-10-14. Accepted, with the row added in the same commit as this decision.

`docs/dependencies.md` -> Terraform now lists `hashicorp/random` 3.9.1, constrained to `~> 3.7`,
MPL-2.0, as task 1.1's test-user password generator. Checked against the repository rather than taken
on trust: `infra/modules/idp-cognito/versions.tf` and `infra/envs/poc/idp/versions.tf` both require
`hashicorp/random` at `~> 3.7`, both `.terraform.lock.hcl` files pin 3.9.1 under that constraint, and
`random_password.test_user` feeds both `aws_cognito_user.this.password` and
`aws_ssm_parameter.test_user_password.value` in `infra/modules/idp-cognito/main.tf`. The provider that
each lock file pins carries a `LICENSE.txt` reading Mozilla Public License 2.0. The row names the two
directories, because `infra/bootstrap` and `infra/envs/poc/apps` pin `hashicorp/aws` only: task 1.8's
"if it generates anything" turned out to be nothing.

Four readings beyond the row itself:

- **A managed `random_password` is the right generator**, and the request's reasoning holds. Checked
  again on 14 October 2026 with `terraform providers schema -json` against the cached providers, no
  network and no apply: in `hashicorp/aws` 6.68.0 `aws_cognito_user.password` is `optional` and
  `sensitive` with no `write_only`, so Terraform refuses an ephemeral value there, and the Cognito
  user resource puts the password in state whatever generates it. `random_password` and
  `aws_secretsmanager_random_password` both exist as ephemeral resources, and neither can feed that
  attribute for the same reason. The `aws_secretsmanager_random_password` data source would return a
  new value on every plan and needs `secretsmanager:GetRandomPassword`, which the CI plan role does
  not have. The state bucket is private, versioned, encrypted and owner-enforced
  (`infra/bootstrap/state.tf`), and the CI plan role can read it, so these passwords are test-user
  passwords and nothing else.
- **`~> 3.7` stands as written.** Nothing in the repository says why the floor is 3.7 rather than a
  lower 3.x, and this decision does not invent a reason. The floor only matters to a resolve that
  cannot reach a newer 3.x, and both lock files pin 3.9.1 regardless.
- **The licence goes in the Note**, because the Terraform table has no Licence column, and
  `hashicorp/aws` gains "MPL-2.0" in the same edit so that the two rows say the same kind of thing.
- **The row carries its own date.** The file's header still reads "Checked on 11 October 2026", because
  moving it would claim that every other row was rechecked on the 13th. The `hashicorp/random`
  registry page joins Sources with its own read date.

**What stays with workstream 1.** The SSM parameter keeps `value` rather than the write-only
`value_wo`: `random_password.result` and the Cognito user's `password` are in state either way, so the
switch would change the exposure not at all and add a `value_wo_version` to manage. Task 1.1 is not
done, and nothing here makes it so: it is written and validated, not applied. Applying the identity
root and then the discovery-document check remain workstream 1's, and this request was the only thing
task 1.1 was owed by the integrator.

No contract, no output and no ADR. `contracts/infra-outputs.schema.json` -> `testUsers` names the
parameter and never the password, which is still true. A provider row is trivially reversible and
generating a password with the standard `random` provider is not surprising, so neither ADR criterion
is met; the trade-off that is real, the password living in state, is forced by the AWS provider's
schema rather than chosen, and the module's comment and the identity root's README already record it.
