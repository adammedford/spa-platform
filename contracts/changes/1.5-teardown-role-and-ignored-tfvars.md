# Change request 1.5: who the teardown role is, and two files `.gitignore` does not cover

- **Raised by:** workstream 1, AWS and IaC
- **Tasks:** 1.5, and 1.7 which runs the teardown it depends on, and 6.7 and 6.9 which walk it
- **Date:** 2026-10-13
- **Status:** decided, 2026-10-14. See the Decision section below and ADR-0014.

## 1. "The teardown role" is named in a frozen contract and defined nowhere

`contracts/s3-layout.md` says the bucket policy "denies deletes there to everyone but the teardown
role", and the 1.5 row repeats it. No root creates such a role, `infra/bootstrap` creates only the
state bucket and the read-only CI plan role, and `contracts/infra-outputs.schema.json` has no field
for it. So there is a name three tasks depend on with nothing behind it.

It is the same shape as change request 1.6a: a string that two owners have to agree on or the check
is vacuous. Here the consequence is sharper than a vacuous check, because the policy is a `Deny`:

- name no principal, and **nothing can ever delete under `apps/`**. `teardown.sh` cannot empty the
  bucket, `terraform destroy` fails on it, and P-05 ("a query for the platform tag returns no
  resources") can never pass.
- name the wrong principal, and a release can be replaced in two steps, which is what ADR-0009 and
  P-04 exist to prevent.

### What task 1.5 implemented

`modules/cell` takes `teardown_principal_arns`, a list with **no default** and a validation that
refuses an empty one, and the platform root passes it through from a variable with no default. So an
apply fails loudly until someone names a principal, rather than creating a bucket that cannot be
emptied.

That is a placeholder, not an answer. It puts the decision in a `terraform.tfvars` that is not
committed, which means the value behind a frozen contract's rule lives only on whoever's
workstation applied it last.

### Decision asked for

One of these, and workstream 1 has no preference strong enough to argue for:

1. **A role in `infra/bootstrap`**, beside the CI plan role, with its ARN in that root's outputs.
   The two bootstrap resources already outlive teardown, which is exactly what a teardown role has
   to do; it cannot live in a root that teardown destroys. This is the option that makes the ARN
   reproducible rather than remembered.
2. **A field in `contracts/infra-outputs.schema.json`**, if the role is created elsewhere, so that
   `teardown.sh` and workstream 6 read it rather than infer it. That contract is frozen at G1a, so
   this is the integrator's edit either way.
3. **Say it is the operator's own principal by design**, and that naming it in `terraform.tfvars` is
   the intended answer. Then the only thing missing is a sentence in `contracts/s3-layout.md` saying
   so, because "the teardown role" currently reads as a thing the platform creates.

## 2. `.gitignore` covers no `*.tfvars` and no `backend.hcl`

`.gitignore` ignores `.terraform/`, `*.tfstate` and `*.tfstate.*`. It does not ignore:

- `terraform.tfvars` — the platform root's holds an IAM role ARN, which carries the account id, and
  `infra/bootstrap`'s holds a GitHub repository and trusted principal ARNs;
- `backend.hcl` — holds the state bucket's name, which carries the account id.

Both roots ship a `.example` of each, so the convention is clearly that the real files are local.
Nothing stops `git add -A` from committing them. This is not a leaked credential — an account id is
not a secret — but it is an account identifier in a public repository, and the fix is two lines.

`.gitignore` is a root file and so the integrator's.

### Decision asked for

Add to `.gitignore`:

```gitignore
*.tfvars
!*.tfvars.example
backend.hcl
```

Nothing is blocked meanwhile. Tasks 1.2 and 1.5 are written and statically validated, and neither
has been applied.

## Decision

Integrator, 2026-10-14. Both halves accepted. The role question is decided as **option 1**, with one
addition the request did not ask for: the ARN is derived from the cell name rather than configured,
so no one has to remember or paste it. [ADR-0014](../../docs/adr/0014-teardown-role-in-bootstrap.md)
records it in full, `contracts/s3-layout.md` now defines the term the contract was using, and
`.gitignore` has the three patterns.

### 1. The teardown role

`spa-platform-<cell>-teardown`, created by `infra/bootstrap` beside the CI plan role, tagged as a
bootstrap resource so it stays invisible to the platform query (ADR-0013). Its **name** is derived
from the cell; its **ARN comes from AWS**. The platform root derives the name and looks the role up
with `data "aws_iam_role"`, so a missing or mis-derived role is a plan error rather than a discovery
at teardown — which matters because the ARN lands in a policy *condition*, where nothing validates
it. `teardown.sh` derives the same name and reads no state, which it must, because bootstrap keeps
local state and its outputs exist only on the workstation that applied it. `modules/cell` keeps
`teardown_principal_arns` and its non-empty validation exactly as task 1.5 wrote them — the module
taking the principals as input was right, and only the root's defaulting was missing. The root's own
variable is `additional_teardown_principal_arns` (default `[]`, concatenated), so an extra principal
is visibly additional and cannot silently replace the only one that can empty the bucket.

The request said workstream 1 had no preference strong enough to argue for. Two things settle it
beyond "bootstrap outlives teardown":

- **Option 2 is the shape ADR-0013 already rejected.** `outputs.json` is written after an apply and
  teardown needs the role when outputs are stale or gone, so reading a teardown constant out of an
  apply artefact is circular. It would also be a new required field in a contract frozen at G1a,
  which `contracts/README.md` sends to the next gate rather than to a decision.
- **Option 3 walks into a trap, which is why the ARN is derived.** `aws:PrincipalArn` carries the
  **role** ARN for a request made by a role session, and the IAM documentation says not to use the
  assumed-role session ARN there — but `aws sts get-caller-identity` prints exactly that session
  form. An operator asked for "your ARN" pastes `arn:aws:sts::…:assumed-role/…`, the `ArnNotLike` in
  `DenyReleaseDeleteExceptTeardown` matches nothing, the deny covers the teardown principal too, and
  the bucket cannot be emptied — found at G3, with the stack up. Checked against the IAM condition
  keys reference on 14 October 2026; the quotation is in ADR-0014.

### 2. `.gitignore`

Added, as three lines rather than the requested four:

```gitignore
*.tfvars
*.tfvars.json
backend.hcl
```

`!*.tfvars.example` is left out because it is not needed: `*.tfvars` matches names ending in
`.tfvars`, and `terraform.tfvars.example` ends in `.example`, so the committed examples were never
at risk. `*.tfvars.json` is added because Terraform reads that form too and the request's reasoning
covers it. The comment above them names this request.

### What stays with workstream 1

All the Terraform, since `infra/` is workstream 1's and the integrator does not write it:

1. the role, its trust policy and its inline policy in `infra/bootstrap`, with a
   `teardown_role_arn` output for humans. Trust comes from its **own** required variable,
   `teardown_trusted_principal_arns`, with no default and a precondition that fails the apply when
   nobody is named — not the CI role's trusted principals, which are a different population — and
   carries an MFA condition with `BoolIfExists`. Not the CI plan role, and not the GitHub Actions
   OIDC provider. Permissions are `s3:DeleteObject` and `s3:DeleteObjectVersion` on
   `<bucket ARN>/apps/*`, plus `s3:ListBucket` and `s3:ListBucketVersions` on the bucket ARN —
   **real ARNs, not the glob `spa-platform-<cell>-*`, which matches no bucket** now that the bucket
   is `spa-platform-<cell>-<account id>`. Nothing else: destroying the roots runs as the operator.
2. the platform root's derivation of the name, the `data "aws_iam_role"` lookup, and the renamed
   `additional_teardown_principal_arns` (default `[]`), so an apply needs no `terraform.tfvars`
   entry for it.
3. the cell-name validation in **both** roots, identical: 3 to 22 characters,
   `^[a-z0-9][a-z0-9-]{1,20}[a-z0-9]$`, no edge hyphen, with a comment naming where each bound comes
   from. This widens bootstrap rather than tightening `modules/cell`, because a landed test pins 22.
4. the platform root test's `mock_data` block for the lookup, and its variables.
5. `infra/bootstrap/README.md`, which says the root "owns two things and nothing else" and now owns
   three.
6. `infra/bootstrap/terraform.tfvars.example`, whose comment says it is "not ignored by
   `.gitignore`" — which this request's second half makes untrue.
7. the teardown comment in `infra/envs/poc/platform/terraform.tfvars.example`.

Task 1.5 stays not done: it is written and statically validated, not applied. This request was the
only thing it was owed by the integrator.
