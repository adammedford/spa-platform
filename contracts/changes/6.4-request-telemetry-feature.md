# Change request 6.4: a request feature for `rule` and `session_ref`, and the instrument names

- **Raised by:** workstream 6, Verification and operations, during task 6.4
- **Tasks:** 6.4; the stages that would write the feature: 2.3 (host resolution), 3.4 and 3.9
  (sessions, shell gate), 4.3 to 4.5 (request gate, antiforgery), 4.1 and 4.2 (proxy)
- **Date:** 2026-10-13
- **Status:** decided, 2026-10-14. See the Decision section below.

## What is missing

`contracts/telemetry.md` puts `rule` and `session_ref` on the one request log line, and says
`security.rejections` is counted by the same rule id. Stage 2 writes that line once the rest of the
pipeline has returned, so it can read anything a later stage left on the request. Nothing in
`Platform.Abstractions` gives a later stage a place to leave it:

- **`rule`.** The request gate (stage 6), antiforgery (stage 9), the shell gate (stage 8) and the
  proxy (stage 10) each know the rule id they refused under. Today each writes a Warning line of its
  own with a `{Rule}` property (`src/Platform.Security/MethodAllowlist.cs`,
  `src/Platform.Proxy/UnknownApi.cs`). Those lines reach the log with `rule` and the request's
  `trace_id`, so a refusal can be joined to its request line, but the request line itself cannot say
  which rule fired.
- **`session_ref`.** Only workstream 3 holds the session key. Stage 2 must never see the key (it is on
  the never-logged list), only the reference.
- **The meter and the activity source.** The metrics table names nine instruments and no `Meter`.
  `AddPlatformTelemetry` can only subscribe to a meter by name, and A-03 stops a workstream
  referencing `Platform.Telemetry` to use its meter.

A workstream cannot invent these: a type or a key shared between workstreams is a contract.

## The change

1. In `src/Platform.Abstractions`, a request feature set by stage 2 before it calls the rest of the
   pipeline, and written by any later stage:

   ```csharp
   public interface IRequestTelemetryFeature
   {
       /// <summary>The rule id from contracts/request-gate.md that refused the request, or null.</summary>
       string? Rule { get; set; }

       /// <summary>contracts/telemetry.md: the first 12 hex characters of a SHA-256 of the session key.</summary>
       string? SessionRef { get; set; }
   }
   ```

   and a static helper beside it that computes `SessionRef` from a session key, so workstream 3 does
   not hand-roll the truncation and the key never leaves workstream 3.

2. In `contracts/telemetry.md`, under the metrics table: every platform `Meter` and `ActivitySource`
   is named `Platform.<Project>` (for example `Platform.Security` for `security.rejections`), created
   through `IMeterFactory`, and `security.rejections` carries the tag `rule`.

## What task 6.4 did without it

- The request line carries every other field in the contract and leaves `rule` and `session_ref`
  out. Once the feature exists, stage 2 sets it, reads it back after `next()` and adds both fields;
  `tests/Platform.Telemetry.Tests/RequestLineTests.cs` gains one case for each.
- `AddPlatformTelemetry` subscribes to `Platform.*` meters and activity sources already, so a meter
  named as proposed is exported with no further change in workstream 6.
- The formatter writes a `{Rule}` property as `rule`, so the refusal lines the stages write today
  already carry the field under the contract's name.

## Decision

Integrator, 2026-10-14. Both items accepted, applied in the same commit as this decision, with three
corrections to the request's own detail.

### 1. The carrier

`IRequestTelemetryFeature` goes into `src/Platform.Abstractions` as asked, as a typed request
feature. The alternatives were considered and rejected: a shared `HttpContext.Items` key is just as
much a cross-workstream contract but untyped, and tags on the request's `Activity` exist only when a
listener created one and would export `session_ref` to traces as a side effect. `IAppFeature` is the
precedent and the idiom stage 4 already uses.

A stage writes the feature null-conditionally, because a stage's own test project runs without stage
2 and a missing feature must cost nothing. `src/Platform.Testing` gains
`SettableRequestTelemetryFeature` so that every workstream asserts "this stage set rule X" the same
way, against the doubles, which is how a test id names a behaviour here.

`Rule` is written only by the stage that ends the request with a rejection. Nothing enforces
write-once: a rejection ends the pipeline, so at most one stage writes it, and a setter that threw
would turn a logging mistake into a 500.

### 2. `session_ref` and its helper

`SessionRef.Of(key)` sits beside the feature. The contract fixes the hash and the length and leaves
the encoding and the case open, so the helper fixes them: SHA-256 over the key's UTF-8 bytes,
lowercase hex, first 12 characters. Both had to be settled once, or two writers would produce two
references for one session. It is the framework's SHA-256, not custom cryptography, and the key
passes through the method without leaving workstream 3's code.

An empty key is refused rather than hashed. It would otherwise produce a perfectly valid-looking
reference that every empty-keyed request shared.

### 3. The instruments, and who counts `security.rejections`

The `Platform.<Project>` naming rule and `IMeterFactory` are accepted, and `contracts/telemetry.md`
now carries both. **The request's example is wrong under this decision** and is changed: it offered
`Platform.Security` for `security.rejections`, but stage 2 counts that metric, not workstream 4, so
it lives on `Platform.Telemetry`. The rule's live examples are `Platform.Registry` for `registry.*`
and `Platform.Identity` for `auth.*`.

Stage 2 counts `security.rejections` itself, from the feature's `Rule` after `next()`, tagged `rule`
and `app_id`. One owner then guarantees that the count equals the request lines carrying a rule.
The alternative was six stages in three projects each taking an `IMeterFactory` and declaring the
same instrument, which exports as several streams under different scopes. Both tag sets are bounded:
twelve rule ids, and the registry's apps.

### Landing it between gates

This is the first contract type added since `skeleton-v1`, so the rule it lands under is now written
into `contracts/README.md` rather than left in one decision: prose and a new type that changes no
existing stage, owner or entry point's signature land on the integrator's decision; anything else
waits for the next gate. I-7 stated the first half of that rule and this request uses the second.

Nothing already built against the skeleton has to change to keep compiling, and the feature carries
fields the G1a telemetry contract already required. Waiting for `contracts-v1` would hold task 6.4
and six landed stages behind G0, which needs AWS.

The feature is frozen as soon as it lands, with no `[Freeze("G1b")]` marker and outside the G1b draft
set. The `session_ref` formula is in a G1a contract and the feature touches neither `SessionRecord`
nor `ISessionStore`; the freeze tests at G1b assert an empty draft set, so a new G1b marker would
only have to be removed again. `tests/Platform.Abstractions.Tests/PublicSurfaceTests.cs` gains both
type names, which is what makes an addition here a decision rather than a convenience.

### Who writes the fields, corrected from the request

The request's list of writers was taken from the plan rather than from the code, and it is wrong in
three places. Read from the code, matching each rule id in `contracts/request-gate.md` to the file
that raises it:

| Rule ids | Where | Task | Stage | The id in the code today |
| --- | --- | --- | --- | --- |
| `host.unknown` | `src/Platform.Hosting/HostResolution.cs` | 2.3 | 4 | No. It writes a bare 404 and logs nothing, so the id appears nowhere in `src/` |
| `path.invalid`, `path.reserved` | `src/Platform.Hosting/Assets.cs` | 2.4 | 10 | Yes, on its own Warning line |
| `path.invalid`, `path.reserved`, `gate.*` including `gate.method` | `src/Platform.Security/RequestGate.cs` | 4.3 | 6 | Yes |
| `csrf.token` | `src/Platform.Security/PlatformAntiforgery.cs` | 4.4 | 9 | Yes |
| `api.unknown` | `src/Platform.Proxy/UnknownApi.cs` | 4.1 | 10 | Yes |
| `auth.callback`, `auth.session` | not written yet | workstream 3 | 7, 8 | n/a |
| `gate.method` | `src/Platform.Security/MethodAllowlist.cs` | 4.6 | **1** | Yes, but it cannot reach the feature. See below |

So: **2.4 is added**, because it already rejects and the request left it out. **4.5 is removed**,
because it only sets security headers and never rejects. **4.2 is removed**: when no access token can
be had, that 401 reports the session's state rather than a broken rule and `request-gate.md` has no
id for it, so `Rule` stays null there and no id is invented — a new id would change a G1a contract and
would have to wait for a gate under the rule above. That is the narrow case only; it is not a general
licence to leave `Rule` null on a 401, and in particular stage 8's unauthenticated fetch has an id,
`auth.session`. And **"3.4 and 3.9" is corrected to workstream 3's ticket-store adapter**:
`ISessionStore` has no `HttpContext`, so 3.4 cannot write the field. By plan row 3.3 the adapter holds
both the key and the request; exactly where it writes is workstream 3's design, and none of it starts
before `contracts-v1`.

**Task 4.6 is not a writer, and finding that out cost this decision its one real error.** The
grilling and the first draft of this section both listed 4.6 among the stages to add, on the strength
of its rule id being in the code. It is, but `MethodAllowlist` runs in **stage 1**:
`UsePlatformForwardedHeaders` installs it (`src/Platform.Security/PlatformSecurityExtensions.cs`) and
`src/Gateway/Program.cs` calls that before `app.UsePlatformTelemetry()`. Stage 2 has not created the
feature yet, so the null-conditional write would be a permanent no-op, and the request never reaches
stage 2 at all. Checked by running it: a `TRACE` over a raw socket produces the
`Platform.Security.MethodAllowlist` warning line carrying `rule=gate.method` and **no** request line,
where a plain `GET /` on the same run produces one.

So a stage-1 405 is logged with its rule id and is neither counted nor on a request line, which
`contracts/request-gate.md`'s "Each rejection is logged and counted under a rule id" does not allow.
That hole predates this request — nothing counted `security.rejections` before — but this decision is
what makes it load-bearing, so it is named rather than left to be discovered. Closing it means either
moving stage 1 behind stage 2 or giving `MethodAllowlist` a counter of its own: the first changes the
order in `contracts/pipeline.md`, and the second contradicts "one owner counts this metric" above.
Both are gate-level decisions under the rule this request writes into `contracts/README.md`, so
neither is taken here. It is filed for G1b. The other `gate.method` site,
`src/Platform.Security/RequestGate.cs` at stage 6, is task 4.3's and is covered by the `gate.*` row.

Task 2.3 sets `host.unknown` on the feature and adds no Warning line of its own. Unknown hosts are
the cheapest traffic for anyone to send, so a line each would let a stranger flood the log; the
request line and the counter record the rejection once. Every stage that already writes its own
Warning line keeps it: those lines carry which check and which header, which the request line does
not, and `RequestGateTests` and `AssetTests` assert on them. Removing one is its owner's choice and
not a contract matter.

### What is left, and to whom

Workstream 6 finishes task 6.4: stage 2 creates the feature, reads it back after `next()`, logs
`rule` and `session_ref`, counts `security.rejections`, and `RequestLineTests` covers each against
the `Platform.Testing` implementation. `RequestTelemetry`'s own doc comment, which says these two
fields are not on the line "yet" and points at this request, goes with it, as does `MeterName`'s,
which calls itself the meter "every platform instrument lives under" — the naming rule above now
forbids exactly that. 6.4 is done at that
point: it owns stage 2, and the six follow-ups are other owners' stages, which workstream 6 proves
again in the composed suites at 6.3.

**Vocabulary.** The contracts and the metric name say "rejection"; the code's log messages say
"refused". A contract uses one word, and that word is "rejection". "Rule id" is used in three files
and defined in none. Both are proposed for `GLOSSARY.md` in the overnight ticket and left for Adam to
apply; nothing here depends on them.

No ADR. The feature is the framework's own idiom and `IAppFeature` already uses it, so it is not
surprising; counting in stage 2 is reversible inside one project; and the between-gates rule is a
process rule, which belongs in `contracts/README.md` beside the freeze it qualifies.
