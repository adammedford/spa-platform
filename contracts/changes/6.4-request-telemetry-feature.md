# Change request 6.4: a request feature for `rule` and `session_ref`, and the instrument names

- **Raised by:** workstream 6, Verification and operations, during task 6.4
- **Tasks:** 6.4; the stages that would write the feature: 2.3 (host resolution), 3.4 and 3.9
  (sessions, shell gate), 4.3 to 4.5 (request gate, antiforgery), 4.1 and 4.2 (proxy)
- **Date:** 2026-10-13
- **Status:** open

## What is missing

`contracts/telemetry.md` puts `rule` and `session_ref` on the one request log line, and says
`security.rejections` is counted by the same rule id. Stage 2 writes that line once the rest of the
pipeline has returned, so it can read anything a later stage left on the request. Nothing in
`Platform.Abstractions` gives a later stage a place to leave it:

- **`rule`.** The request gate (stage 6), antiforgery (stage 9), the shell gate (stage 8) and the
  proxy (stage 10) each know the rule id they refused under. Today each writes a Warning line of its
  own with a `{Rule}` property (`src/Platform.Security/MethodAllowlist.cs`,
  `src/Platform.Proxy/UnknownApi.cs`). Those lines reach the log with `rule` and the request's
  `trace_id`, so a refusal can be joined to its request line, but the request line itself cannot say
  which rule fired.
- **`session_ref`.** Only workstream 3 holds the session key. Stage 2 must never see the key (it is on
  the never-logged list), only the reference.
- **The meter and the activity source.** The metrics table names nine instruments and no `Meter`.
  `AddPlatformTelemetry` can only subscribe to a meter by name, and A-03 stops a workstream
  referencing `Platform.Telemetry` to use its meter.

A workstream cannot invent these: a type or a key shared between workstreams is a contract.

## The change

1. In `src/Platform.Abstractions`, a request feature set by stage 2 before it calls the rest of the
   pipeline, and written by any later stage:

   ```csharp
   public interface IRequestTelemetryFeature
   {
       /// <summary>The rule id from contracts/request-gate.md that refused the request, or null.</summary>
       string? Rule { get; set; }

       /// <summary>contracts/telemetry.md: the first 12 hex characters of a SHA-256 of the session key.</summary>
       string? SessionRef { get; set; }
   }
   ```

   and a static helper beside it that computes `SessionRef` from a session key, so workstream 3 does
   not hand-roll the truncation and the key never leaves workstream 3.

2. In `contracts/telemetry.md`, under the metrics table: every platform `Meter` and `ActivitySource`
   is named `Platform.<Project>` (for example `Platform.Security` for `security.rejections`), created
   through `IMeterFactory`, and `security.rejections` carries the tag `rule`.

## What task 6.4 did without it

- The request line carries every other field in the contract and leaves `rule` and `session_ref`
  out. Once the feature exists, stage 2 sets it, reads it back after `next()` and adds both fields;
  `tests/Platform.Telemetry.Tests/RequestLineTests.cs` gains one case for each.
- `AddPlatformTelemetry` subscribes to `Platform.*` meters and activity sources already, so a meter
  named as proposed is exported with no further change in workstream 6.
- The formatter writes a `{Rule}` property as `rule`, so the refusal lines the stages write today
  already carry the field under the contract's name.
