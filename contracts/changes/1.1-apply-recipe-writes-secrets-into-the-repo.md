# Change request 1.1: the documented apply recipe writes secrets into the repository

- **Raised by:** workstream 1, AWS and IaC (found by the overnight grilling of ticket 02)
- **Tasks:** 1.1 and 1.8, whose READMEs carry the recipe; 1.0, whose apply comes first; and task 1.9,
  whose policy checker reads the same plans
- **Date:** 2026-10-15
- **Status:** decided, 2026-10-15. Both integrator items have landed; the workstream 1 follow-ups
  are outstanding. See the Decision section below.

## The problem

The three infrastructure READMEs document the apply as `terraform plan -out=<name>.tfplan` with a
relative path, so the plan file lands **inside the working tree**. A Terraform plan's `after` values
hold what the apply will write. For these two roots that means:

- the identity root's `idp.tfplan` carries **every generated test-user password**, because task 1.1
  generates them and writes them to Parameter Store;
- the apps root's equivalent carries **every OAuth client secret**, because task 1.8 creates one
  secret parameter per app definition.

At the request's base `070e3fae`, no `.gitignore` pattern matched either file. It covered
`.terraform/`, `*.tfstate` and `*.tfstate.*`; the pending teardown-role change added `*.tfvars`,
`*.tfvars.json` and `backend.hcl`. This PR adds plan patterns as item 1 below.

So `git add -A` after a plan commits credentials. `-refresh=false` does not change it: the values are
in the plan because the plan is going to write them.

**This is live the moment the first apply sitting runs**, and nothing has been applied yet, so the
window is still open. It is the only item in tonight's 143 questions that can leak a credential
rather than cost time.

## What is asked of the integrator

Two root-file edits. Both are the integrator's because `.gitignore` and `.github/` are.

1. **Add to `.gitignore`:**

   ```gitignore
   # Terraform plan files: a plan's `after` holds the values the apply will write,
   # so the identity root's carries test-user passwords and the apps root's carries
   # client secrets. Change request 1.1.
   *.tfplan
   *.tfplan.json
   ```

   Belt and braces alongside item 2, not instead of it: a plan written outside the tree cannot be
   committed, and a pattern catches the operator who ignores the instruction.

2. **Require, in the CI job that runs the plan policy checker (P-01 to P-03, and P-07 if Q45 is
   taken), that the identity and apps plans and their JSON are piped to the checker inside the job
   and never uploaded as a workflow artifact.** An uploaded plan artifact is a credential in the
   Actions retention store, readable by anyone who can read the run.

## Why this is a change request and not an edit

The leak is in files workstream 1 owns, but the two fixes that make it structural — the ignore
pattern and the CI rule — are root and `.github/` files, which AGENTS.md reserves to the integrator.
Filing the whole thing as one request keeps the two halves from landing a week apart.

## Blocking

**Yes, for the apply sitting only.** Tasks 1.1 and 1.8 are written and statically validated; neither
can be applied safely until item 1 lands or the operator keeps every plan file outside the tree by
hand. Nothing in the repository is blocked, and no test waits on it.

## Decision

Integrator, 2026-10-15. Both halves accepted and landed.

### 1. The ignore patterns

`*.tfplan` and `*.tfplan.json` are in `.gitignore`, with a comment naming this request. Checked
rather than assumed: `git ls-files | git check-ignore --stdin` is empty, so nothing tracked became
ignored, and no `.example` or example JSON is matched.

### 2. The CI rule, as a check rather than a sentence

Asked for as a requirement on the CI job. It landed as `.github/plan-secrecy.py`, run beside the
steering check, because the step it has to constrain **does not exist yet**: the plan-policy step is
a placeholder that no-ops until task 1.9 writes `tools/scripts/plan-policy.sh`. A requirement
recorded only in prose is one task 1.9 would read after writing the convenient form, and
`.github/steering.py` already makes the argument against that: "A paragraph asking for the rule is
not the same as a check enforcing it."

The check conservatively refuses direct Terraform/OpenTofu `plan` and `show` commands in
workflow YAML, local composite actions and shell helpers under `.github/` and `tools/`, plus
`actions/upload-artifact` references. Plan production is disabled today rather than approved by
an unsafe string-prefix check. Quoted values, command continuations, helper files and stdout/tee
variants are regression fixtures, run in CI beside the guard. The existing cache stores only
`~/.nuget/packages`; task 1.9 must review caches alongside artifacts.

This is a source regression check, not an interpreter or a security sandbox. Arbitrary dynamic
commands, downloaded actions, scripts in other languages and deliberately obfuscated commands
are outside its proof. Task 1.9 must replace the conservative stop with a reviewed end-to-end
producer/consumer implementation before plan generation is enabled, including consumer diagnostics,
logs, caches and uploads. Nothing here claims a runtime plan pipeline has already been verified.
HashiCorp explicitly documents that `show -json` reveals sensitive values in plaintext:
https://developer.hashicorp.com/terraform/cli/commands/show#json-output

The future required shape remains: save the binary plan outside the checkout under the runner's
private temporary directory, pipe JSON directly into the policy checker, and never log or upload
either representation. There is no runtime pipeline to exercise until task 1.9 lands.

Change request 1.9 removed the placeholder step that carried item 2's future shape (2026-10-22);
`plan-secrecy.py` enforces the rule, and any credentialed pipeline (ADR-0016 decision 4) must
meet it.

### What stays with workstream 1

- **every recipe naming the project it applies into**, by sourcing `tools/aws-project.env` before
  its first `terraform` line:

  ```bash
  set -a; . tools/aws-project.env; set +a   # AWS_PROFILE and the Region, or the wrong project
  ```

  Added 2026-10-16. A sitting applied the bootstrap root into the wrong project, because the default

  match the project's one selected Region;
- the same recipes beginning at **step 0: apply `infra/bootstrap`**, since nothing has ever been
  applied and there is no re-apply.
