# Change request 1.1: the documented apply recipe writes secrets into the repository

- **Raised by:** workstream 1, AWS and IaC (found by the overnight grilling of ticket 02)
- **Tasks:** 1.1 and 1.8, whose READMEs carry the recipe; 1.0, whose apply comes first; and task 1.9,
  whose policy checker reads the same plans
- **Date:** 2026-10-15
- **Status:** open

## The problem

The three infrastructure READMEs document the apply as `terraform plan -out=<name>.tfplan` with a
relative path, so the plan file lands **inside the working tree**. A Terraform plan's `after` values
hold what the apply will write. For these two roots that means:

- the identity root's `idp.tfplan` carries **every generated test-user password**, because task 1.1
  generates them and writes them to Parameter Store;
- the apps root's equivalent carries **every OAuth client secret**, because task 1.8 creates one
  secret parameter per app definition.

No `.gitignore` pattern matches either file — not on `origin/main`, and not in the integrator's
working-tree version of `.gitignore`. `.gitignore` covers `.terraform/`, `*.tfstate` and
`*.tfstate.*`, and the pending teardown-role change adds `*.tfvars`, `*.tfvars.json` and
`backend.hcl`. Nothing covers `*.tfplan`.

So `git add -A` after a plan commits credentials. `-refresh=false` does not change it: the values are
in the plan because the plan is going to write them.

**This is live the moment the first apply sitting runs**, and nothing has been applied yet, so the
window is still open. It is the only item in tonight's 143 questions that can leak a credential
rather than cost time.

## What is asked of the integrator

Two root-file edits. Both are the integrator's because `.gitignore` and `.github/` are.

1. **Add to `.gitignore`:**

   ```gitignore
   # Terraform plan files: a plan's `after` holds the values the apply will write,
   # so the identity root's carries test-user passwords and the apps root's carries
   # client secrets. Change request 1.1.
   *.tfplan
   *.tfplan.json
   ```

   Belt and braces alongside item 2, not instead of it: a plan written outside the tree cannot be
   committed, and a pattern catches the operator who ignores the instruction.

2. **Require, in the CI job that runs the plan policy checker (P-01 to P-03, and P-07 if Q45 is
   taken), that the identity and apps plans and their JSON are piped to the checker inside the job
   and never uploaded as a workflow artifact.** An uploaded plan artifact is a credential in the
   Actions retention store, readable by anyone who can read the run.

## What stays with workstream 1

`infra/` is workstream 1's, so the recipe itself is theirs to fix:

- `infra/bootstrap/README.md`, `infra/envs/poc/idp/README.md` and
  `infra/envs/poc/apps/README.md`: change every documented `plan -out=` to a path **outside the
  repository**, and say in one line why, so the next person does not helpfully shorten it back.
- The same READMEs' recipes should begin at **step 0: apply `infra/bootstrap`**. The current text
  reads "if `infra/bootstrap` was already applied, re-apply it"; nothing in this platform has ever
  been applied, so there is no re-apply, and the state bucket every other root's backend needs does
  not exist yet.

## Why this is a change request and not an edit

The leak is in files workstream 1 owns, but the two fixes that make it structural — the ignore
pattern and the CI rule — are root and `.github/` files, which AGENTS.md reserves to the integrator.
Filing the whole thing as one request keeps the two halves from landing a week apart.

## Blocking

**Yes, for the apply sitting only.** Tasks 1.1 and 1.8 are written and statically validated; neither
can be applied safely until item 1 lands or the operator keeps every plan file outside the tree by
hand. Nothing in the repository is blocked, and no test waits on it.
