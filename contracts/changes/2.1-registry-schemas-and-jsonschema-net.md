# Change request 2.1: JsonSchema.Net now runs in the gateway, and the gateway image cannot see `contracts/`

- **Raised by:** workstream 2, Hosting and registry
- **Tasks:** 2.1, and 2.2, 2.6 and 1.7 after it
- **Date:** 2026-10-13
- **Status:** open

Task 2.1 has landed without either change below. Neither blocks it. Both are statements or build
steps in integrator files that 2.1 has made incomplete.

## 1. `docs/dependencies.md` lists two users of JsonSchema.Net. There are now three

Line 63 gives JsonSchema.Net's users as "Schema tests, `spactl`". Plan row 2.1 asks for a "schema
check" in the one library the gateway and `spactl` share, so `src/Platform.Registry` now references
`JsonSchema.Net` (the pinned 8.0.5, with no version change). That puts the engine in the gateway
process. Open decision D-1 recommends against that, and says so only as a narrowing of 2.1 that the
integrator would have to accept. That has not happened.

What 2.1 did to keep D-1 cheap: only `src/Platform.Registry/RegistrySchemas.cs` touches the engine.
Whatever D-1 decides, whether another engine or none in the gateway, changes that one file.

**Asked:** add `Platform.Registry` (gateway and `spactl`) to the JsonSchema.Net row, and decide D-1
when convenient.

## 2. The gateway image builds from `src/` only

`src/Gateway/Dockerfile` copies `src/` and the root build files into its build stage, not
`contracts/`. Platform.Registry embeds the contract schemas, so it cannot `Include` them from
`../../contracts` without breaking the image build. Task 1.7 would be the first to find that.

What 2.1 did: it embeds byte-for-byte copies under `src/Platform.Registry/Schemas/`.
`tests/Platform.Registry.Tests/SchemaCopyTests.cs` fails CI when a copy differs from its contract or
a contract schema has no copy, so the copies cannot drift. A contract change therefore needs its copy
refreshed in the same merge (`cp contracts/*.schema.json src/Platform.Registry/Schemas/`).

**Asked, optional:** add `COPY contracts/*.schema.json contracts/` to the Dockerfile's build stage.
Workstream 2 would then switch the `EmbeddedResource` to link `../../contracts/*.schema.json` and
delete the copies and their guard.

## 3. Two integers have no upper bound the model can hold (raised in review)

`revision` and `apis[].timeoutSeconds` are `"type": "integer"` with a minimum and no maximum, and
draft 2020-12 also accepts `30.0` and `3e1` as integers. The validator now reads every such spelling
and reports a value beyond Int64 (`revision`) or beyond a `TimeSpan` (`timeoutSeconds`, above
922337203685 seconds) as `integer-out-of-range` instead of throwing. That is a rule the README's
table does not list.

**Asked, optional:** either add a row to contracts/README.md "Rules that JSON Schema cannot express"
for it, or give both properties a `maximum` in `registry.schema.json` (the plan states none for the
timeout, so any maximum is the integrator's reading).
