# Change request 2.1: JsonSchema.Net now runs in the gateway, and the gateway image cannot see `contracts/`

- **Raised by:** workstream 2, Hosting and registry
- **Tasks:** 2.1, and 2.2, 2.6 and 1.7 after it
- **Date:** 2026-10-13
- **Status:** decided, 2026-10-14. See the Decision section below.

Task 2.1 has landed without either change below. Neither blocks it. Both are statements or build
steps in integrator files that 2.1 has made incomplete.

## 1. `docs/dependencies.md` lists two users of JsonSchema.Net. There are now three

Line 63 gives JsonSchema.Net's users as "Schema tests, `spactl`". Plan row 2.1 asks for a "schema
check" in the one library the gateway and `spactl` share, so `src/Platform.Registry` now references
`JsonSchema.Net` (the pinned 8.0.5, with no version change). That puts the engine in the gateway
process. Open decision D-1 recommends against that, and says so only as a narrowing of 2.1 that the
integrator would have to accept. That has not happened.

What 2.1 did to keep D-1 cheap: only `src/Platform.Registry/RegistrySchemas.cs` touches the engine.
Whatever D-1 decides, whether another engine or none in the gateway, changes that one file.

**Asked:** add `Platform.Registry` (gateway and `spactl`) to the JsonSchema.Net row, and decide D-1
when convenient.

## 2. The gateway image builds from `src/` only

`src/Gateway/Dockerfile` copies `src/` and the root build files into its build stage, not
`contracts/`. Platform.Registry embeds the contract schemas, so it cannot `Include` them from
`../../contracts` without breaking the image build. Task 1.7 would be the first to find that.

What 2.1 did: it embeds byte-for-byte copies under `src/Platform.Registry/Schemas/`.
`tests/Platform.Registry.Tests/SchemaCopyTests.cs` fails CI when a copy differs from its contract or
a contract schema has no copy, so the copies cannot drift. A contract change therefore needs its copy
refreshed in the same merge (`cp contracts/*.schema.json src/Platform.Registry/Schemas/`).

**Asked, optional:** add `COPY contracts/*.schema.json contracts/` to the Dockerfile's build stage.
Workstream 2 would then switch the `EmbeddedResource` to link `../../contracts/*.schema.json` and
delete the copies and their guard.

## 3. Two integers have no upper bound the model can hold (raised in review)

`revision` and `apis[].timeoutSeconds` are `"type": "integer"` with a minimum and no maximum, and
draft 2020-12 also accepts `30.0` and `3e1` as integers. The validator now reads every such spelling
and reports a value beyond Int64 (`revision`) or beyond a `TimeSpan` (`timeoutSeconds`, above
922337203685 seconds) as `integer-out-of-range` instead of throwing. That is a rule the README's
table does not list.

**Asked, optional:** either add a row to contracts/README.md "Rules that JSON Schema cannot express"
for it, or give both properties a `maximum` in `registry.schema.json` (the plan states none for the
timeout, so any maximum is the integrator's reading).

## Decision

Integrator, 2026-10-14. All three items accepted, applied in the same commit as this decision.

1. **D-1 is closed, and its recommendation to keep the engine out of the gateway is rejected.**
   JsonSchema.Net 8.0.5 runs in the gateway process through `src/Platform.Registry`. This README's
   "Rules that JSON Schema cannot express" makes the one shared library the guarantee that the
   gateway and `spactl` cannot disagree, and several security rules live only in the schema: the
   source `'*'` and `'unsafe-eval'` in every policy directive, `'unsafe-inline'` and `data:` in
   `script-src`, `additionalProperties: false`, and the `host`, `upstream` and `clientSecretRef`
   patterns. Narrowing 2.1 would leave the gateway weaker than `spactl` on those rules, or duplicate
   them in C#, and N-14 needs a forbidden source rejected whole. The engine parses a document the
   plan already has the gateway trust. `docs/dependencies.md` records the decision, its revisit
   trigger ("8.x stops receiving a fix we need") and why it is not an ADR: in shipping code
   `RegistrySchemas.cs` is the only file that touches the engine, which is the whole of the gateway's
   and `spactl`'s exposure to it. `tests/Contracts.Tests` and `fixtures/Fixtures.Tests` call it
   directly too, and a swap would touch them; neither ships. The `JsonSchema.Net` row now names its three direct users,
   `Platform.Registry` among them, and says that `spactl` reaches the engine through it. That
   settles what change request 5.5 left open for 2.1 to decide.

2. **`src/Gateway/Dockerfile` copies `contracts/*.schema.json` into the build stage**, after the
   restore so that a schema change does not re-resolve every package. Workstream 2 should now link
   `../../contracts/*.schema.json` as the `EmbeddedResource` and delete
   `src/Platform.Registry/Schemas/` and `tests/Platform.Registry.Tests/SchemaCopyTests.cs`, which is
   filed as a follow-up and is a prerequisite of task I-6. The reason is ownership, not neatness:
   I-6 changes the bytes of three schema files, `SchemaCopyTests` fails until their copies are
   refreshed, and `.github/path-ownership.py`, which `.githooks/pre-push` runs, refuses a push whose
   diff spans the integrator's paths and workstream 2's. "A contract change needs its copy refreshed
   in the same merge" therefore cannot be done within the ownership rules, and one `COPY` line
   removes the problem for good. `tests/Platform.Registry.Tests` already reaches out of its own
   directory for `contracts/` with a relative `Include`, which is the part that has to work; it does
   so as `None` with `CopyToOutputDirectory`, not as an `EmbeddedResource`.

3. **`integer-out-of-range` becomes a row in this README**, and no `maximum` is added to
   `registry.schema.json`. Prose lands between gates; a `maximum` would narrow a contract frozen at
   G1a and bake a runtime limit into the document format. The "no upper bound" bullet now points at
   the row, so the two cannot contradict each other.

**What the real timeout ceiling is, established by running it.** The grilling read .NET's
`CancellationTokenSource.CancelAfter` documentation and inferred a ceiling near `Int32.MaxValue`
milliseconds, with a risk that YARP would throw on a schema-valid value. Both halves were then
checked by running them, on .NET 10.0.12 with YARP 2.3.0:

- `CancelAfter(TimeSpan)` accepts up to `UInt32.MaxValue - 1` milliseconds, so the largest whole
  second it takes is 4,294,967 (49.7 days). It throws `ArgumentOutOfRangeException` above that, and
  for `TimeSpan.MaxValue`.
- YARP never reaches that ceiling. Its `ActivityCancellationTokenSource` holds the activity timeout
  in an `Int32` of milliseconds and **saturates** at `Int32.MaxValue`. `IConfigValidator`
  accepts every value tried, up to the validator's 922,337,203,685 seconds, and a real forward
  through `IHttpForwarder` succeeds at every one. Nothing throws.

So the predicted exception does not exist, and the actual defect is silence: at `timeoutSeconds`
above 2,147,483 (24.855 days) the registry says one thing and the proxy applies another, with no
error and no log. Those numbers are `Yarp.ReverseProxy` 2.3.0 on .NET 10.0.12, measured on
14 October 2026, and they live here rather than in `contracts/README.md` so that a version bump does
not edit a contract. The README states the rule and says in as many words that the rule is not
implemented yet, because it is the file other owners build to and a requirement written in the
present tense would read there as a guarantee. That is still a value the platform cannot apply, so it belongs under
`integer-out-of-range`, with the number owned by the runtime rather than the schema. The validator's
present bound, `TimeSpan.MaxValue.Ticks / TicksPerSecond`, is wrong by about 430,000 times.
Tightening it is workstream 2's and 4's follow-up, which includes a test that fails on the clamp
rather than quoting this decision.

**Task 2.1 is done.** Its done-when was met when it landed. Two follow-ups were opened by this
decision and do not reopen it: workstream 2 links the contract schemas, deletes the copies and their
guard, and corrects the comments this decision makes stale -- two that call D-1 open
(`Platform.Registry.csproj`, `RegistrySchemas.cs`), two that say the image build sees only `src/`
(`Platform.Registry.csproj`, and `SchemaCopyTests.cs`, which is deleted anyway) and one that says
`integer-out-of-range` is not a README row (`RegistryIssue.cs`); workstreams 2 and 4 pin the timeout
ceiling by test and have the validator refuse above it. The deployed tier has a second ceiling, the ALB idle timeout, which is
unknown until task 1.3 lands and does not change the hermetic bound.

**Two statements elsewhere now lag this decision.** `README.md`'s pointer said
`docs/dependencies.md` held "two open decisions"; it holds one, and the row now says "open and
closed" rather than counting. `docs/plan/03-workstreams-and-tasks.md` still calls the JSON Schema
validator an open decision. That file is a frozen export and is never edited in place
(`contracts/README.md`, opening), so it is left alone and noted here: the plan records what was open
on 11 October 2026, and this file records what was decided after it.

**Glossary.** "Schema check" and "the validator's rules" are both used without being defined, and
telling them apart is what item 1 turns on. A glossary entry for the pair is proposed in the
overnight ticket and left for Adam to apply.
