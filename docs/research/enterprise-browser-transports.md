# Connections used by enterprise browser workloads

- **Ticket** [#1495, Which connection patterns do enterprise browser workloads require?](https://github.com/adammedford/spa-platform/issues/1495), on [map #1494](https://github.com/adammedford/spa-platform/issues/1494).
- **Date** 2026-11-23
- **Branch** `research/enterprise-browser-transports`, based on `83a6c3fa40546ee4c5d35040804774e90f9641db`
- **Method** Read first-party application code, product and client documentation, and protocol specifications. This was a source review. No workload was deployed, provider tried or protocol tested.

## Answer in brief

1. A live screen can use a one-way HTTP response, repeated HTTP reads or a duplex socket. JupyterHub uses EventSource to show server-start progress. JupyterLab’s collaboration extension uses WebSockets to exchange edits and cursor positions.[^progress][^collaboration]
2. A transport name alone understates the work. SignalR negotiates among transports. A gRPC-Web client needs RPC framing and final status. An MQTT dashboard needs broker subscriptions and topic authorization.[^signalr][^rpc][^broker]
3. Recovery depends on what survived the disconnect. An SSE event ID, a Matrix sync token, an upload byte range and a download representation validator each identify different state. Background push, peer media and adaptive video introduce other endpoints that the page need not keep connected to its application server.[^progress][^poll][^upload][^download][^push][^rtc][^hls]

## Which connections do the workloads use?

The Jupyter rows cite implemented features. Microsoft Graph documents an available service API. Other rows name the framework, service or specification from which the example is drawn. The order lookup, incident alert and town hall illustrate documented capabilities. These sources establish neither frequency of use across enterprises nor compatibility with this gateway.

| Workload | Who opens each connection, and what it carries | Identity or access constraint | What the user experiences on that connection |
| --- | --- | --- | --- |
| Start a notebook server and watch its progress | JupyterHub’s pending page opens an EventSource GET to the Hub progress endpoint. The Hub streams UTF-8 SSE events to the page. | The endpoint requires `read:servers`. Native EventSource accepts a URL and a credentials option. The browser can use a same-origin session cookie, but the constructor offers no custom authorization header. | Progress arrives before the HTTP response ends. On a reconnect, EventSource can send the last event ID supplied by the server. Recovering missed updates requires the producer to interpret it and retain the relevant events. JupyterHub documents progress, without promising that history.[^progress] |
| Show an assistant’s answer as it is generated | In Vercel AI SDK’s HTTP example the browser sends a fetch POST containing the chat message to its application API. The response body streams text deltas using SSE framing. | Fetch supports configured credentials and request headers. The example connects to the application's chat endpoint. | The page renders partial text and can abort its read. Resuming a turn needs retained server-side stream state and a resume endpoint. In the SDK's resumable setup, canceling generation needs an explicit server operation.[^chat] |
| Co-edit a notebook and see colleagues’ cursors | Each editor opens a WebSocket to the Jupyter collaboration server. Yjs-compatible document synchronization and awareness information cross it in both directions. | Jupyter documents shared access to the environment, including cell execution. Browser WebSocket handshakes can carry eligible cookies. JavaScript supplies a URL and optional subprotocols. | Every editor can send changes and receive peer updates during the same connection. The collaboration layer synchronizes the shared document and displays cursor presence.[^collaboration] |
| Keep a team room’s timeline current | A Matrix client long-polls its homeserver with HTTP GET `/sync`. Each request ends with a batch of events or a timeout, then the client opens the next request. | The homeserver authenticates the client with a Matrix access token. | The next request passes the previous `next_batch` as `since`. A limited room timeline can still have a gap, which the client fills by fetching message history.[^poll] |
| Update a shared operations dashboard through a SignalR hub | The browser normally POSTs to negotiate with the hub endpoint, then carries SignalR hub messages over WebSockets, SSE or long polling according to available transports. SSE and polling use separate HTTP POSTs for client sends. | A signed-in browser can use its cookie. When configured for bearer auth, the browser client uses an access-token query parameter for WebSockets and EventSource. | The application gets hub calls even when the transport falls back. Connection lifetime matters for authorization. By default a connected client can outlive token expiry. Further HTTP requests need valid credentials.[^signalr] |
| Look up an order and watch fulfillment updates | A generated browser stub sends a gRPC-Web HTTP request. In the official example Envoy translates it to native gRPC for the service. | Call metadata can carry authorization. The proxy and service must agree on which metadata reaches the service. | The official JavaScript client supports unary calls in binary or text mode. Server streaming requires `grpcwebtext`. It can cancel a call. Final status can be framed in the response body. Client and bidirectional streaming are outside this client’s documented modes.[^rpc] |
| Watch readings from a piece of equipment | A device publishes to an IoT broker, for example with MQTT over TLS. A browser dashboard separately subscribes to that topic using MQTT over secure WebSocket (WSS). The broker forwards matching readings. | In AWS IoT Core the device can use an X.509 certificate. The WSS client can use AWS Signature Version 4. Topic policies distinguish subscribing from receiving data. | Multiple viewers can follow one publisher. The device’s connection can stay up while a viewer leaves. AWS documents watching device messages with its console test client and documents WSS as a supported client transport.[^broker] |
| Resume a large document upload | A client POSTs to Microsoft Graph to create an upload session, then PUTs sequential byte ranges to the returned upload URL. | The creation request uses a bearer token with file-write permission. The returned URL authorizes the upload until expiry. Graph instructs clients to omit the bearer header on the PUTs. | After a lost response, the client can GET session status and continue from a missing range in `nextExpectedRanges`. Progress measures bytes the service accepted.[^upload] |
| Resume a large document download | A browser client can retrieve a preauthenticated Microsoft Graph download URL, then GET a byte `Range` from that URL. | The initial Graph request is authorized. The download URL itself is a short-lived credential. | A partial response (`206`) supplies the requested bytes. A server may return the full file. For HTTP servers supporting validators, `If-Range` with a strong ETag lets the client restart with the full representation when the file changed.[^download] |
| Notify an on-call engineer after the tab closes | With permission, the browser creates a push subscription and the app passes its endpoint to its server. Later the app server POSTs to the browser’s push service. The browser delivers a push event to the origin’s service worker. | The subscription belongs to a service worker registration. VAPID can bind it to the sending application server’s public key. The sender and the human recipient have distinct identities. | The worker can display a notification while the page is closed. The push service can retain pending messages while the device is offline, within their time to live.[^push] |
| Share a screen with a remote support agent | Each browser exchanges session descriptions and ICE candidates through application-defined signaling, for example over HTTPS or WSS. WebRTC sends screen media over secure RTP on the selected media path, directly between peers or via a TURN relay. | The application controls access to signaling. The sharing browser requires the user to select a display surface and grant capture permission for that use. DTLS-SRTP establishes media keys. | A successful signaling exchange can still leave the peers without a usable media path. When a direct path is unavailable, a relay can carry the media.[^rtc] |
| Watch a live company town hall at different bitrates | A browser player such as HLS.js makes HTTP requests to the media origin or CDN for playlists and media segments. A live player reloads the media playlist to discover later segments. | Access covers multiple related files. CloudFront documents signed cookies scoped to a set of private HLS files as one option. | The player can choose a bitrate variant and fetch its segments. This adds adaptive, cacheable media delivery across many requests.[^hls] |
