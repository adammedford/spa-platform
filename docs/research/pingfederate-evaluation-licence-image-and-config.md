## Answer in brief

1. **The licence.** An individual gets the key, not a licence file: sign on at
   pingidentity.com with a Ping Identity account (create one if needed), choose *Support and
   Community*, and on the support portal profile click *Register for DevOps Program*; the
   `PING_IDENTITY_DEVOPS_USER` (the account email) and `PING_IDENTITY_DEVOPS_KEY` (a UUID) are
   emailed, and re-registering resends the same pair rather than regenerating it ([devops-reg]). The
   licence is generated by the container at its first start: hook `17-check-license.sh` calls
   `https://license.pingidentity.com/devops/license` with `product: PF`, `version`, `devops-user`,
   `devops-key` and `devops-app: <image version>` headers, writes `pingfederate.lic` into the
   instance's `server/default/conf`, and fails the container (exit 17) unless
   `PING_IDENTITY_ACCEPT_EULA=YES` ([hook-17], [pf-readme]). Ping's terms: "short-lived (30 days)",
   "must not be used in production deployments", and "can only be used with images published in
   the last 90 days" ([prereqs]); the subscription agreement's Trial Products clause adds "only use
   test or mock data" and no Personal Information ([sub-agreement]). Nothing read admits or forbids
   a cloud-hosted standalone container: the DevOps pages name Docker Desktop, any Linux Docker host,
   Compose and Kubernetes/Helm as places the images run ([prereqs], [devops-key]), and the agreement
   restricts by use, not by location. A mounted `pingfederate.lic` at
   `/opt/in/instance/server/default/conf/pingfederate.lic` takes precedence over the key
   ([existing-lic]). Renewal: with no `/opt/out` volume every start is a `START` and fetches a fresh
   licence; with a volume the second start is a `RESTART`, which does not run the licence hook, and
   PingFederate warns in the console, emails (if configured) and "Has Stopped Processing Requests"
   once "the current license and the grace period, if any, had lapsed" ([entrypoint], [hook-01],
   [hook-10], [hook-20], [lic-events]). The grace period's length, a per-key limit on renewals and
   the licence's feature set: not found.
2. **The image.** `pingidentity/pingfederate`: the newest build is sprint `2610` (2026-11-03),
   tags `2610-13.1.4` and `13.1.4-latest` share manifest digest
   `sha256:435da455bf2a4cc71f4413fcce6811f8e5b46ce2c6fe7a5be83add4d35f0302b` with `linux/amd64` and
   `linux/arm64` images of about 610 MB; `latest` and `edge` point at the same 13.1.4 today but
   slide, sprint tags are "promised to be immutable" ([hub-tags], [release-tags]). UBI builds became
   multi-arch in 2610 ([relnotes-2610]). Ports 9031 (runtime HTTPS) and 9999 (admin console and API)
   ([pf-readme], [dockerfile]). Memory: the image sets `MAX_HEAP_SIZE=384m` and
   `JAVA_RAM_PERCENTAGE=75.0` ("DO NOT set to 100%") ([pf-readme]); the product's own minimum is
   "4 GB of RAM" with "at least 1.5 GB ... available to PingFederate", two to four cores, Graviton 2
   qualified and AWS Fargate named among platforms it "has run well on" ([sysreq]). Start time: no
   figure on any page; the only bounds are the post-start hook's `ADMIN_WAITFOR_TIMEOUT=300` s and the
   Docker `HEALTHCHECK` start period of 241 s ([pf-readme], [dockerfile]). Persistence: the image
   copies the product bits and the staged profile into `/opt/out/instance` on every `START`, so with
   no volume a container starts clean from its profile every time; a volume turns the next start into
   a `RESTART` that keeps the instance and skips the profile merge unless `SERVER_PROFILE_UPDATE=true`
   ([hook-03], [hook-06], [hook-07]).
3. **Configuration as code.** One payload, three carriers. The admin API (`/pf-admin-api/v1`,
   `X-XSRF-Header: PingFederate`, Basic auth after setup) has an endpoint for every setting the
   ticket lists ([admin-api-doc], [openapi]); a server profile's `instance/bulk-config/data.json` is
   that same API, posted by hook `85-import-configuration.sh` to `POST /bulk/import?failFast=false`
   with `X-BypassExternalValidation: true` after hook 83 has accepted the licence agreement and
   created the first administrator ([hook-81], [hook-83], [hook-85]); and Terraform provider v1.11.0
   wraps the same endpoints as resources (`pingfederate_oauth_client` with `client_auth.type =
   "PRIVATE_KEY_JWT"` and `jwks_settings.jwks`, `require_pushed_authorization_requests`,
   `redirect_uris`, `oidc_policy.logout_mode = "OIDC_BACK_CHANNEL"` and `back_channel_logout_uri`;
   `pingfederate_oauth_access_token_manager` with `selection_settings.resource_uris`;
   `pingfederate_openid_connect_policy`; `pingfederate_oauth_server_settings` with
   `track_user_sessions_for_logout` and `par_status`; `pingfederate_password_credential_validator`;
   `pingfederate_idp_adapter`; `pingfederate_oauth_idp_adapter_mapping`;
   `pingfederate_oauth_access_token_mapping`) ([tf-client], [tf-atm], [tf-oidc], [tf-as],
   [tf-pcv], [tf-adapter], [tf-adapter-map], [tf-atm-map]). `form_post` is not a setting at all: it
   is the `response_mode` request parameter ([authz-endpoint]). All three can do every item with no
   console click. **Recommendation:** the fixture in `fixtures/pingfederate/` is a server profile
   (`data.json.subst` plus `env_vars`-free `${VAR}` substitution), mounted at `/opt/in` by the
   compose stack, because it is applied by the container itself before the readiness file exists,
   needs no second tool and no reachable admin port, and is what a sitting can also mount or bake;
   the cell takes the same profile baked into a derived image (`COPY pingfederate/. /opt/in/.`),
   with secrets as `${VAR}` tokens fed from Parameter Store, because an ECS task has no bind mount
   and its admin port is reachable only through the tunnel ([anatomy], [profiles], [subst]).
   Terraform suits later drift and the cell's second-day changes, not first start: the provider needs
   an authenticated admin on a reachable 9999, which the hooks create only when a `data.json` exists
   or `CREATE_INITIAL_ADMIN_USER=true` ([hook-81], [tf-index]). Section 3.4 lists what the
   profile mechanism costs: `metadata.pfVersion` "should match", the getting-started profile's
   literal keys, and the Simple PCV's `username`-only contract.
4. **Admin credentials and TLS.** The first administrator is `administrator`, created headlessly by
   hook 83 with `POST /administrativeAccounts` from `PING_IDENTITY_PASSWORD` (default
   `2FederateM0re`, Ping's published value), which that hook reads from the environment alone
   (`test -z "${PING_IDENTITY_PASSWORD}" && container_failure 83`), the moment
   `PUT /license/agreement` returns 200 on a new server; 401 means an admin already exists
   ([hook-83], [pf-readme]). The runtime certificate is a system-generated default;
   a PKCS12 or PEM key pair is imported with `POST /keyPairs/sslServer/import` (`fileData`,
   `password`, `format`) and activated with `PUT /keyPairs/sslServer/settings`
   (`runtimeServerCertRef`, `activeRuntimeServerCerts`), which the getting-started profile does in
   `data.json` and Terraform does with `pingfederate_keypairs_ssl_server_key` and
   `pingfederate_keypairs_ssl_server_settings`; PingFederate picks the certificate by SNI against CN
   and SANs and falls back to the default ([openapi], [ssl-certs], [tf-sslkey], [tf-sslsettings]).
   So a `.test` host can be served under the project's own certificate: `tools/scripts/certs.sh`
   issues a wildcard for `*.spa-poc.test` from a local authority, and either that leaf or one more
   leaf for the provider host (`idp.spa-poc.test`, say) is imported as above; the issuer must also be
   set, as `federation_info.base_url` (`/serverSettings`) and `PF_ENGINE_PUBLIC_HOSTNAME`, to that
   public host ([tf-server-settings], [pf-readme], [certs-sh]).

## 1. The licence

### 1.1 What an individual obtains, and how

The DevOps registration page is the only primary page with the human steps ([devops-reg]); the
checklist in section 5 reproduces them. Its substance: a Ping Identity account (free registration at
`pingidentity.com/en/account/register.html`), sign-on with *Support and Community* selected in the
*Select Account* list, the support portal profile at `support.pingidentity.com/s/`, the right-side
menu item *Register for DevOps Program*, and "the DevOps credentials will be forwarded to the email
address associated with your Ping Identity account". The example values have the form
`PING_IDENTITY_DEVOPS_USER=jsmith@example.com` and a UUID key. Lost credentials: "click Register for
DevOps Program again, and the same DevOps credentials will be resent". The DevOps team "has no access
to the Ping Identity account system". Whether a personal email address is accepted at account
registration: not found (the registration form was not fetched).

The prerequisites page frames the key's purpose: "You must have a product license to run our
images", and the evaluation licence is "obtained with a valid DevOps user key"; "you are issued
credentials that automate the process of retrieving an evaluation product license" ([prereqs]). There
is no page where a human downloads the licence file; the FAQ says the DevOps team provides "a
temporary license through the DevOps program" and that production use needs a purchased licence
([faq]). (`pingcli license` appears in the search index as a deprecated command; its page was not
read, so it is not relied on.)

### 1.2 The terms

- "Evaluation licenses are short-lived (30 days) and must not be used in production deployments."
  ([prereqs])
- "Evaluation licenses can only be used with images published in the last 90 days. If you want to
  continue to use an image that was published more than 90 days ago, you must obtain a product
  license." ([prereqs]) How the server knows the image's age is not documented; the fetch sends
  `devops-app: ${IMAGE_VERSION}`, and `IMAGE_VERSION` carries the build date in `YYMMDD`
  ([hook-17], [release-tags]), which is consistent with a server-side check but is an inference, not
  a documented rule.
- Docker Hub: "Before running the software on this image, you must obtain a license"; by passing
  `PING_IDENTITY_ACCEPT_EULA=Yes` "the image user agrees that their use of the Software in the Docker
  image will be governed by the license agreement terms", and absent a paid licence "the Software is
  deemed a 'Trial Product' under those terms" ([hub-page]).
- The subscription agreement (effective 2025-05-09), clause 12.10 Trial Products: a trial is "until
  the earlier of (a) the end of the trial period ..., (b) the start date of any subscription ..., or
  (c) termination of the Trial Product by Ping Identity in its sole discretion"; "A trial period may
  be extended upon mutual agreement"; "Customer is not permitted to use Trial Products in connection
  with Personal Information. Customer represents and warrants that it will only use test or mock
  data with Trial Products"; provided "AS IS" ([sub-agreement]). Clause 1.2 grants a licence "to
  install the Software, in machine-readable form only, and to use the Software solely for Customer's
  business use" with no location term ([sub-agreement]).
- **A standalone cloud container (an ECS task):** no page read admits or forbids it. The DevOps
  pages describe Docker Compose ("any Docker Desktop installation or Linux system with Docker and
  `docker compose` installed"), standalone `docker run`, Kubernetes secrets and Helm as the places
  the user and key are consumed ([prereqs], [devops-key]); the agreement restricts by use (test
  data, no personal information, not production). The 13.1 system requirements name "AWS Fargate"
  among virtualisation products PingFederate "has run well on" and qualify "the Graviton 2 processor
  architecture" ([sysreq]). The fixture's users are `alice@spa-poc.test` and `bob@spa-poc.test`
  from `fixtures/cognito/pool.json`, test data by construction.
- Renewal limits per key, the licence's feature set (OAuth and OIDC are assumed, not shown), and a
  grace period's length: not found.

### 1.3 How the licence and the EULA reach the container

The start order is fixed by `entrypoint.sh`: `apply_local_server_profile` (copies `/opt/in` to the
staging directory on every start), `01-start-server.sh` (which runs 02 remote profile, 03 run plan,
04 variables, 05 templates, 06 product bits, 07 apply profile), then `10-start-sequence.sh` on
`RUN_PLAN=START` or `20-restart-sequence.sh` on `RESTART`, `50-before-post-start.sh`,
`80-post-start.sh` in the background, and `exec run.sh` ([entrypoint], [hook-01], [lib-in-dir]).
`RUN_PLAN` is `START` when `/opt/out/instance/bin/run.sh` does not exist yet, `RESTART` when it does
([hook-03]). `10-start-sequence.sh` runs `17-check-license.sh` ([hook-10]); `20-restart-sequence.sh`
runs only `21-update-server-profile.sh`, a hook that is not in the image's tree and is therefore
skipped by `run_if_present` ([hook-20], [lib-run-hook], [builds-tree]).

`17-check-license.sh` ([hook-17]), verbatim in its branches:

1. `LICENSE_FILE="${LICENSE_DIR}/${LICENSE_FILE_NAME}"`, which for this image is
   `/opt/out/instance/server/default/conf/pingfederate.lic` (`LICENSE_DIR=${SERVER_ROOT_DIR}/server/default/conf`,
   `LICENSE_FILE_NAME=pingfederate.lic`, `LICENSE_SHORT_NAME=PF`, `LICENSE_VERSION=${LICENSE_VERSION}`
   baked at build) ([pf-readme], [dockerfile]).
2. If the file exists: unless `MUTE_LICENSE_VERIFICATION` is true, a network query to
   `https://license.pingidentity.com/devops/check-license` with the licence `ID` and the image version.
3. Else, if `PING_IDENTITY_DEVOPS_USER` and `PING_IDENTITY_DEVOPS_KEY` are set: up to four attempts at
   `https://license.pingidentity.com/devops/license` with headers `product`, `version`,
   `devops-user`, `devops-key`, `devops-app: ${IMAGE_VERSION}`, `devops-purpose: get-license`,
   output to the licence file. On success, `PING_IDENTITY_ACCEPT_EULA` must be `yes`/`y` (case
   folded) or `container_failure 17 "You must accept the EULA by providing the environment variable
   PING_IDENTITY_ACCEPT_EULA=YES"`. On failure the error JSON's `.error` is printed and the file
   removed.
4. Else `container_failure 17 "License File absent"` with the ALERT block the troubleshooting page
   reproduces ([troubleshoot]).

So the licence reaches PingFederate as a file on disk before `run.sh` starts, and no API call is
involved in licensing a fresh container. The key is read from the environment, or from
`~/.pingidentity/config` when that file is passed with `--env-file` / `env_file` ("the container
attempts to find the DevOps registration information first in the DevOps property file ... If the
DevOps registration information isn't found there, the container checks for environment variables")
([devops-key]); Kubernetes examples expect a secret named `devops-secret` ([devops-key]). The image
redacts the key in its own variable dump (`PING_IDENTITY_DEVOPS_KEY_REDACT=true`,
`*** REDACTED ***`), but `PING_DEBUG=true` makes hook 17 `cat` the licence file into the log
([pf-readme], [lib-echo-vars], [hook-17]). The `docker run` example also mounts `--tmpfs
/run/secrets`, the `SECRETS_DIR` ([pf-readme]).

**An existing licence file** mounted at `/opt/in/instance/server/default/conf/pingfederate.lic` wins:
"If you have provided license files via the volume mount and a DevOps User/Key, it will ignore the
DevOps User/Key" ([existing-lic]). The layered-profiles page shows the same file carried as its own
profile layer, and `docker cp` of `pingfederate.lic` out of a running evaluation container
([layered]). The product itself records a console-imported licence at
`<pf_install>/pingfederate/server/default/conf/pingfederate.lic` and renames the previous one with a
timestamp ([lic-replace]).

### 1.4 Expiry

- "If the license specifies an expiration date, the license expires at the beginning of that day."
  ([lic-events])
- "The administrative console displays a warning message ahead of the expiry of your license." A new
  file can be imported "if your license key is going to expire, or has expired recently"
  ([lic-mgmt]). Headless: `PUT /license` ([openapi]; `pingfederate_license.file_data`, [tf-license]).
- Notification events (optional email): warning "60 days ahead of the expiration"; "The current
  license expired" on expiry; and "PingFederate Has Stopped Processing Requests" when "The current
  license and the grace period, if any, had lapsed" ([lic-events]). The grace period's length: not
  found.
- For a container with no `/opt/out` volume, expiry is moot: every start fetches a new 30-day
  licence (section 1.3). For a cell task that outlives 30 days without a restart, PingFederate fails
  closed per the shutdown event; a restart with no persistent volume is the renewal. A task with a
  persistent volume would `RESTART` and keep the lapsed file (the open item "the 30-day licence
  against a cell that outlives a sitting" on #944).

## 3. Configuration as code, headless

### 3.1 One payload, three carriers

**The admin API.** `https://<pf_host>:9999/pf-admin-api/api-docs/` documents it and
`/pf-admin-api/v1/swagger.json` is its OpenAPI; "you must include `X-XSRF-Header: PingFederate` in
all requests", JSON for PUT and POST, HTTP Basic with an administrative account whose roles bound
what it may change ([admin-api-doc]). Before any account exists "you can make four unauthenticated
administrative API requests": `GET /license/agreement`, `PUT /license/agreement`, `PUT /license`,
`POST /administrativeAccounts` (the first account must hold `USER_ADMINISTRATOR`) ([admin-api]).
"All four administrative roles are required" for `/bulk`, `/configArchive` and `/configStore`
([admin-api-access]). The OpenAPI at `v1310` has every path this ticket needs: `/oauth/clients`,
`/oauth/accessTokenManagers`, `/oauth/accessTokenMappings`, `/oauth/idpAdapterMappings`,
`/oauth/openIdConnect/policies`, `/oauth/authServerSettings`, `/passwordCredentialValidators`,
`/idp/adapters`, `/keyPairs/sslServer/import`, `/keyPairs/sslServer/settings`, `/virtualHostNames`,
`/serverSettings`, `/license`, `/license/agreement`, `/administrativeAccounts`, `/bulk/export`,
`/bulk/import`, `/configArchive/import` ([openapi]). Authentication is `BasicAuth`, a bearer JWT or
OAuth client credentials ([openapi]); native is the default for new installations
([admin-api-access]).

**A server profile.** A directory laid "over a vanilla installation of pingfederate" whose structure
"must follow that of a pingfederate instance" ([gs-readme]); delivered by `SERVER_PROFILE_URL` (a
git HTTPS URL, with `SERVER_PROFILE_PATH` the subdirectory and optional `SERVER_PROFILE_BRANCH`), by
a bind mount at `/opt/in`, or baked with `COPY pingfederate/. /opt/in/.` ([anatomy], [pf-readme]).
Files ending `.subst` are passed through `envsubst` and renamed; `.subst.default` only when the
target is absent; `.zip.subst` archives are expanded, substituted and re-zipped ([hook-05], [subst]).
Layers: `SERVER_PROFILE_PARENT=<NAME>` names a layer whose own variables are
`SERVER_PROFILE_<NAME>_URL/_PATH/_BRANCH/_PARENT`; the parent-most layer is cloned first and each
child copied over it ("copied ... (not merged)"), the top `SERVER_PROFILE_URL` last ([hook-02],
[layered]). A private repository takes `SERVER_PROFILE_GIT_USER`/`_GIT_PASSWORD` or
`username:token` in the URL, and the URL is redacted in logs when so ([hook-02], [layered]). An
`env_vars` file in the profile is sourced into the container's environment and may "override image
and orchestration variables" (the hook warns unless `# .suppress-container-warning` is present)
([hook-02]). The configuration itself travels in one of two shapes:

- `instance/bulk-config/data.json` (`BULK_CONFIG_DIR=${OUT_DIR}/instance/bulk-config`,
  `BULK_CONFIG_FILE=data.json`): "A PingFederate Admin Console imports a `data.json` on startup if it
  finds it in `instance/bulk-config/data.json`" ([build-profile], [pf-readme]). Mechanically:
  `81-after-start-process.sh` runs `83-configure-admin.sh` when the file exists (or
  `CREATE_INITIAL_ADMIN_USER=true`), then `85-import-configuration.sh`, which posts the file as the
  administrator to `POST /bulk/import?failFast=false` with `X-BypassExternalValidation: true`,
  deletes the file on 200, and exits 85 otherwise (and so kills the container through hook 80's
  `kill 1`) ([hook-81], [hook-85], [hook-80]). The endpoint: "All existing configuration will be
  wiped before the import begins. If any validation errors are found, PingFederate will roll back to
  the previous configuration. The master key set in pf.jwk must include the key in use when the JSON
  configuration was originally exported" ([openapi]). The schema is `{"metadata": {"pfVersion"},
  "operations": [{"resourceType", "operationType": SAVE|DELETE, "items" | "itemIds"}]}` and "the
  DELETE operation is only supported for the /configStore resource type" ([openapi]). The
  getting-started profile's `data.json.subst` carries `/license/agreement`, `/administrativeAccounts`,
  `/keyPairs/sslServer` (with `${...fileData}` and `${...password}` tokens), `/keyPairs/sslServer/settings`,
  `/virtualHostNames`, `/oauth/authServerSettings`, `/session/settings` and more; the baseline
  profile's adds `/oauth/clients`-adjacent resources: `/oauth/accessTokenManagers` (a
  `JwtBearerAccessTokenManagementPlugin` instance named `jwt`), `/oauth/accessTokenMappings`,
  `/oauth/openIdConnect/policies`, `/passwordCredentialValidators` (a `simple` PCV with
  `${..._Password_value}` tokens), `/idp/adapters` (an HTML Form adapter whose `Credential
  Validators` table names the PCV), `/authenticationPolicyContracts`, `/certificates/ca`,
  `/keyPairs/signing` ([gs-data], [baseline-data]). Neither sample contains `/oauth/clients`
  itself, and the `layered-profiles/oauth/pingfederate` layer its compose file names does not exist
  in the repository ([profiles-tree], [layered-compose]); the OpenAPI's `/oauth/clients` and the
  bulk export's "configuration objects" cover it, so this is a gap in the samples, not in the
  mechanism. Export: `GET /bulk/export` as the administrator; "By default, the resulting `data.json`
  from the export contains encrypted values" needing the matching `pf.jwk`, and each can be replaced
  by its plaintext form (`encryptedPassword` → `password`, `fileData` → base64 `.p12`)
  ([build-profile]). Ping's bulk-config tool turns an export into `data.json.subst` plus an
  `env_vars` naming tokens such as
  `${keyPairs_sslServer_items_<id>_<id>_password}` ([build-profile]). Caveat: "Your data.json.subst
  `"metadata": {"pfVersion": "10.1.2.0"}` should match the PingFederate profile version"
  ([build-profile]); the getting-started sample still says `10.1.2.0` and the baseline `12.0.0.0`
  against a 13.1.4 image, and the endpoint says older exports "can be imported" but are "not a
  supported way of upgrading" ([gs-data], [baseline-data], [openapi]).
- A configuration archive (`data.zip`, from `/configArchive`) dropped as the profile's
  `instance/server/default/data` directory: "works better for profile layering" and is present on
  engines at start, but keys live in a `.jks` and encrypted data is scattered and master-key-bound
  ([build-profile], [profiles]).

**Terraform `pingidentity/pingfederate` v1.11.0.** The registry's current version is `1.11.0`,
published 2026-10-14 ([tf-registry], [tf-releases]); v1.9.0 (2026-07-22) "Added support for
PingFederate 13.1, and removed support for EOL versions (versions prior to 12.2.0)", and the provider
"supports versions 12.2 through 13.1" ([tf-releases], [tf-index], [tf-support]). Provider block:
`https_host` (the admin host, e.g. `https://localhost:9999`), `admin_api_path` (default
`/pf-admin-api/v1`), `product_version` (required, e.g. `"13.1"`), and either `username`/`password`,
OAuth client credentials or `access_token`; `insecure_trust_all_tls` ("should not be enabled outside
of testing") or `ca_certificate_pem_files`; `x_bypass_external_validation_header` ([tf-index]). Its
getting-started guide starts PingFederate with the DevOps image and the getting-started profile and
waits for "PingFederate is up" before applying ([tf-getting-started]). The resources for this
ticket, with the attribute that carries each setting, are in 3.2. Bootstrap resources exist
(`pingfederate_license_agreement.accepted`, `pingfederate_license.file_data`,
`pingfederate_administrative_account`), but the provider block itself requires credentials, and
whether it can make the four unauthenticated calls against a server with no account was not found
([tf-license-agreement], [tf-license], [tf-admin-account], [tf-index]).

### 3.3 Which carrier suits the fixture, and which the cell

Judged on: configured after `compose up` with no second step; whether 9999 must be reachable from
where the tool runs; how secrets travel; and what a sitting can reproduce by hand.

**`fixtures/pingfederate/` for the compose stack and a sitting: a server profile, mounted at
`/opt/in`.** The profile is applied by the container itself, before `/tmp/ready` exists and before
the gateway's health checks pass, so the stack has no ordering problem and no second tool; the file
is `envsubst`-templated, so the gateway's public JWK, the users' passwords and the runtime
certificate's PKCS12 enter as `${VAR}` tokens from the compose environment, never as literals in the
repository ([subst], [hook-05], [gs-data]); the layout is the same one Ping's own examples and the
Terraform guide use ([pf-readme], [tf-getting-started]); a sitting reproduces it with one `docker
run` whose arguments are the compose service's (section 6); and `/opt/in` is re-copied on every
start, so an edited fixture takes effect on the next `up` with no volume to clear ([lib-in-dir]).
Its costs are in 3.4: a `data.json` is the whole configuration ("All existing configuration will be
wiped"), its `pfVersion` should match the image, and it is written by hand or from a `/bulk/export`
of a console-built instance that is then variablised. The alternative, Terraform against the running
container, needs an admin account the hooks create only with a `data.json` present or
`CREATE_INITIAL_ADMIN_USER=true`, a `terraform apply` step after "PingFederate is up", provider state
on the workstation, and `insecure_trust_all_tls` or the project CA; the compose stack would gain a
Terraform runner image or a host step the suites cannot start. It is right for a second-day change
and for drift detection, not for first start.

**The cell: the same profile, baked into a derived image.** An ECS task has no bind mount from a
workstation, and its 9999 is private to the VPC and the tunnel, so neither `/opt/in` from a
checkout nor a workstation-run `terraform apply` at task start fits. The profile reaches the task
either baked (`COPY pingfederate/. /opt/in/.` from `pingidentity/pingfederate:2610-13.1.4`, a
derived image in the cell's registry, which is also what the release-tags page recommends against
Hub churn) or pulled at start with `SERVER_PROFILE_URL` and a repository token ([anatomy],
[release-tags], [hook-02]). Secrets: the same `${VAR}` tokens, fed as task environment from Parameter
Store, as the gateway container already does for its own values; the DevOps user and key are two
more such values ([hook-05]; `infra/modules/cell/ecs.tf`). The licence fetch needs HTTPS egress to
`license.pingidentity.com` at every `START`; the task security group allows 443 out, and the private
half's NAT exists only behind `multi_task` (`infra/modules/cell/network.tf`), so the shape ticket
decides the subnet. Terraform's place in the cell is the provider run through the tunnel after the
task is healthy, for changes that should not rebuild the image, with `product_version = "13.1"`
and `ca_certificate_pem_files` pointing at the project's authority ([tf-index]).

### 3.4 Constraints the mechanism imposes on the fixture

- **The getting-started profile is a starting point, not a base layer.** Its `env_vars` sets
  literal `serverSettings_systemKeys_items_*_keyData`, a literal SSL keystore and its password, and
  `PING_IDENTITY_PASSWORD` to Ping's default, all in a public repository ([gs-env-vars]); a fixture
  that layers over it inherits public keys. The fixture generates its own system keys, keystore and
  admin password, and ships its own `pf.jwk` only if it keeps encrypted values (plaintext `password`
  and `fileData` forms need no master key) ([build-profile]).
- **`metadata.pfVersion` should match the image** ([build-profile]). The fixture pins one, and the
  pins sweep noted on #944 gains the image tag and that string together.
- **The Simple PCV's contract is `username`.** The HTML Form adapter's core attribute is `username`
  and the Simple PCV table holds a username and password per row ([tf-adapter], [tf-pcv]); the map
  wants `email`, `name` and a stable `sub` matching `fixtures/cognito/pool.json`. Those come from the
  OIDC policy's and the access token mapping's `attribute_contract_fulfillment` with a `TEXT` or
  `EXPRESSION` source (OGNL expressions need the Expression Admin role, which hook 83 grants the
  first administrator; whether expressions are enabled by default was not checked) or from a data
  store ([tf-oidc], [tf-atm-map], [admin-api-access], [hook-83]). A question for the fixture ticket,
  not decided here.
- **Audience per resource.** "Audience Claim Value" is per ATM and static ([atm-instance]), so
  `orders` and `reports` are two ATMs, each with its resource URI in `selectionSettings.resourceUris`
  and the client allowed both (or `restrictToDefaultAccessTokenManager=false`) ([openapi]).
- **The admin API is destructive at the bulk level** and per-resource otherwise; the hooks import
  once, then delete the file ([hook-85]). Re-running a changed `data.json` means a fresh container
  (no `/opt/out` volume), which is the compose stack's natural shape.
- **Logs.** `PING_DEBUG=true` prints the licence file; `VERBOSE=true` runs the common hooks with
  `set -x`; and `DEBUG=true` turns on `start_debug_logging`, which brackets the `curl` calls of hooks
  83 and 85 and so echoes command lines carrying the admin password ([hook-17], [hook-83],
  [hook-85], [lib-run-hook]). The stack leaves all three unset (N-16).

## 4. Admin credentials and TLS

**The administrator.** `83-configure-admin.sh`: `PUT /license/agreement` with `{"accepted": true}`
and no credentials; on `200` ("new server found, must create admin") it requires
`PING_IDENTITY_PASSWORD` and posts `{"username": "administrator", "password": ..., "roles":
["ADMINISTRATOR","USER_ADMINISTRATOR","CRYPTO_ADMINISTRATOR","EXPRESSION_ADMINISTRATOR","DATA_COLLECTION_ADMINISTRATOR"]}`
to `/administrativeAccounts`; on `401` "Found existing admin PingFederate instance"; on `403`
"License already accepted on this cluster"; `409` from the account post is tolerated ([hook-83]).
The hook runs only when a `data.json` is present or `CREATE_INITIAL_ADMIN_USER=true` ("The initial
admin user will only be created on the first startup of the server after the license is accepted")
([hook-81], [pf-readme]). `PING_IDENTITY_PASSWORD` defaults to `2FederateM0re` in the image and in
every Ping example ([pf-readme], [gs-readme], [compose-example]). Hook 83 reads it from the
environment only, so the value must be set there (a profile's `env_vars` can set it, as
getting-started does, at the cost of putting it in the profile); the `get_value ... true` fallback
to `PING_IDENTITY_PASSWORD_FILE` is used by hooks 81 and 85, which authenticate the bulk import and
the cluster calls, not by the account creation ([hook-83], [hook-81], [hook-85], [lib-get-value]).
Whether `pingsecrets.lib.sh` exports a `/run/secrets` file into the environment before hook 83 runs
was not read in full; the compose snippet in section 6 therefore passes the password as an
environment variable. The getting-started `data.json` additionally SAVEs an `/administrativeAccounts` item `Administrator`
with `${PING_IDENTITY_PASSWORD}` ([gs-data]). Admin API authentication stays `native` unless
`PF_ADMIN_API_AUTHENTICATION` is set ([pf-readme], [admin-api-access]). The fixture sets its own
password; the compose stack passes it by name, never in the file.

**The runtime certificate.** "The first system-generated certificate is the default certificate for
both the administrative console and the runtime server"; imported certificates can be activated for
either or both; with SNI "PingFederate selects the applicable certificate" by exact CN match, then
SAN including wildcards, else the default ([ssl-certs]). Import formats: "In non-BCFIPS mode, we
support PKCS12 and PEM formatted certificates and private keys", PEM with the private key first
([ssl-certs]). Headless: `POST /keyPairs/sslServer/import` with `KeyPairFile {id, fileData (base64
PKCS12 or PEM; raw PEM accepted), format PKCS12|PEM, password}` returns 201, then `PUT
/keyPairs/sslServer/settings` with `runtimeServerCertRef`, `adminConsoleCertRef`,
`activeRuntimeServerCerts`, `activeAdminConsoleCerts` (all four required) ([openapi]); the
getting-started `data.json` does exactly this with `${...fileData}` and `${...password}` tokens
([gs-data]); Terraform: `pingfederate_keypairs_ssl_server_key { key_id, file_data =
filebase64(...), format = "PKCS12", password }` and `pingfederate_keypairs_ssl_server_settings`
([tf-sslkey], [tf-sslsettings]). The DevOps images manage certificates "within the product
configurations" for PingFederate, not through `KEYSTORE_FILE` variables, which are PingData-only
([using-certs]).

**A `.test` host under the project's certificate.** `tools/scripts/certs.sh` keeps a local
authority and issues `*.spa-poc.test` with a SAN block, trusts the authority in the workstation
keychain and imports the leaf to ACM for the cell's ALB ([certs-sh]). PingFederate accepts that leaf
(or a second leaf from the same authority for the provider's own host) as a PKCS12 import, so the
browser trusts the provider as it trusts the apps, and the gateway's own trust of the issuer follows
the machine store or the authority. Two more values must name the public host: `PF_ENGINE_PUBLIC_HOSTNAME`
("engine public hostname that may be used in redirects", default `localhost`) and
`federationInfo.baseUrl` (`pingfederate_server_settings.federation_info.base_url`, "The fully
qualified host name, port, and path ... on which the PingFederate server runs") ([pf-readme],
[tf-server-settings]); virtual host names matter when the host differs from the base URL, including
for `private_key_jwt` `aud` validation ([vhost]). In the cell the provider sits behind the same
internal ALB on its own host, so the ALB's wildcard certificate already covers `*.spa-poc.test`
and the task's own certificate is between ALB and task; the ALB module's target group settings are
the shape ticket's.

## 5. Checklist: the DevOps user key and the evaluation licence

Each step names the page it was read from. Steps 1 to 6 are a human's; 7 onwards are what the
container does, listed so the human knows what to expect.

1. **Have a Ping Identity account.** Sign on at
   `https://www.pingidentity.com/en/account/sign-on.html`; with no account, create one at
   `https://www.pingidentity.com/en/account/register.html`. ([devops-reg])
2. **Choose the right account type at sign-on.** "When signing on, select *Support and Community* in
   the *Select Account* list." ([devops-reg])
3. **Land on the support profile.** After sign-on you are directed to
   `https://support.pingidentity.com/s/`. ([devops-reg])
4. **Register.** "In the right-side menu, click *Register for DevOps Program*." A confirmation
   appears; "the DevOps credentials will be forwarded to the email address associated with your Ping
   Identity account". The pair is `PING_IDENTITY_DEVOPS_USER` (the account's email) and
   `PING_IDENTITY_DEVOPS_KEY` (a UUID). ([devops-reg])
5. **Keep the pair out of the repository.** Either export the three variables in the shell profile
   (`PING_IDENTITY_DEVOPS_USER`, `PING_IDENTITY_DEVOPS_KEY`, `PING_IDENTITY_ACCEPT_EULA=YES`) or write
   them to `~/.pingidentity/config`, which Ping's examples pass with `--env-file` / `env_file`;
   verify with `env | grep PING_IDENTITY`. ([prereqs], [devops-reg], [devops-key]) The repository's
   `.gitignore` is not where this lives; the file is outside the checkout.
6. **If the key is lost**, repeat steps 1 to 4: "the same DevOps credentials will be resent". The
   key is not regenerated by that path; nothing read describes revoking one. For account problems
   the DevOps team "has no access to the Ping Identity account system"; use the support portal.
   ([devops-reg])
7. **There is no manual "generate licence" step.** At the first start of a container with the pair
   and no mounted licence, `17-check-license.sh` fetches the licence from
   `https://license.pingidentity.com/devops/license` and writes
   `/opt/out/instance/server/default/conf/pingfederate.lic`; the log shows "Pulling evaluation
   license from Ping Identity for: Prod License: PF - v13.1" and "Successfully pulled evaluation
   license from Ping Identity". ([hook-17], [pf-readme]) Expect failure text "Unable to download
   evaluation license" with a reason, or the ALERT block, when the pair is wrong or the host is
   unreachable; `curl -k https://license.pingidentity.com/devops/license` from the host should answer
   `{ "error":"missing devops-user header" }` if the network is open. ([troubleshoot])
8. **EULA.** The same hook refuses to continue without `PING_IDENTITY_ACCEPT_EULA=YES` (exit 17); the
   Hub page states what the variable binds you to. ([hook-17], [hub-page])
9. **To keep a copy of the issued file** (for a sitting that must not refetch, or to see its expiry
   line), copy it out of the running container: `docker cp pingfederate:/opt/out/instance/server/default/conf/pingfederate.lic .`
   and mount it next time at `/opt/in/instance/server/default/conf/pingfederate.lic`, which then
   takes precedence over the key. ([layered], [existing-lic]) Treat the file as a secret.
10. **Expect 30 days per issued licence, images no older than 90 days, and no production or
    personal data.** ([prereqs], [sub-agreement])

## 6. The `docker run` and compose snippet for #950

The first smoke uses Ping's getting-started profile (public, with Ping's defaults) so that #950 proves
the licence, the EULA, the arm64 image and the admin API before the fixture exists; the fixture then
replaces `SERVER_PROFILE_URL`/`SERVER_PROFILE_PATH` with a `/opt/in` mount. Each line names its
source. `<...>` are values the human supplies; none is a literal in the repository.

```bash
docker run --name pingfederate --detach \
  --publish 9031:9031 --publish 9999:9999 \
  --memory 2g \
  --env SERVER_PROFILE_URL=https://github.com/pingidentity/pingidentity-server-profiles.git \
  --env SERVER_PROFILE_PATH=getting-started/pingfederate \
  --env PING_IDENTITY_ACCEPT_EULA=YES \
  --env PING_IDENTITY_DEVOPS_USER --env PING_IDENTITY_DEVOPS_KEY \
  --env PING_IDENTITY_PASSWORD="${PF_ADMIN_PASSWORD:?}" \
  --env PF_ENGINE_PUBLIC_HOSTNAME=localhost \
  --tmpfs /run/secrets \
  pingidentity/pingfederate:2610-13.1.4
docker logs -f pingfederate
```

([hook-03]). The `--memory` figure is this document's choice from the two sources named, not a
Ping-published container size. Proof the smoke can take without a console: `curl -k -u
administrator:<password> -H 'X-XSRF-Header: PingFederate' https://localhost:9999/pf-admin-api/v1/version`
(the `X-XSRF-Header` rule, [admin-api-doc]; `/version` is in the OpenAPI, [openapi]) and `curl -k
https://localhost:9031/.well-known/openid-configuration` (the discovery endpoint the gateway reads;
P2-6). Then `docker rm -f pingfederate`.

The same as a Compose v5 service, the shape the L-tier stack will carry:

```yaml
services:
  pingfederate:
    image: pingidentity/pingfederate:2610-13.1.4              # [hub-tags], [release-tags]
    tmpfs: [/run/secrets]                                     # [compose-example]
    ports: ["9031:9031", "9999:9999"]                         # [pf-readme]
    mem_limit: 2g                                             # see --memory above; this document's figure
    environment:
      SERVER_PROFILE_URL: https://github.com/pingidentity/pingidentity-server-profiles.git
      SERVER_PROFILE_PATH: getting-started/pingfederate       # smoke only; the fixture mounts ./pingfederate:/opt/in instead: [anatomy]
      PING_IDENTITY_ACCEPT_EULA: "YES"                        # [hook-17]
      PING_IDENTITY_DEVOPS_USER:                              # from the shell environment: [devops-key]
      PING_IDENTITY_DEVOPS_KEY:
      PING_IDENTITY_PASSWORD:                                 # from the shell environment: [hook-83]
      PF_ENGINE_PUBLIC_HOSTNAME: localhost                    # [pf-readme]
    healthcheck:                                              # the image's own: [dockerfile], [liveness]
      test: ["CMD", "liveness.sh"]
      start_period: 241s
      interval: 31s
      timeout: 29s
      retries: 7
```

Ping's own equivalent passes the pair with `env_file: ${HOME}/.pingidentity/config` and adds a
`pingfederate-out:/opt/out` volume ([compose-example]); the stack omits the volume so every `up` is
a `START` (section 1.3). Compose's `depends_on: condition: service_healthy` on this service is how
the gateway and the suites wait for the provider; the image's health check turns green only after
the profile import ([hook-80], [liveness]).
